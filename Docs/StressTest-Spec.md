# 規格：RF／光耦 控制入口間隔壓力測試工具

> 狀態：ready-for-agent
> 來源：2026-11-20 論文會議紀錄（研究問題一）與 2026-11-21 設計討論

## Problem Statement

研究團隊要在論文第五章回答「在相同加減速指令與不同發送間隔下，光耦（V1）與 433 MHz RF（V2）兩個控制入口能否正確輸出，跑步機是否掉包」。目前手上只有給遊戲用的 Unity 控制器與兩支 Arduino 草稿：

- RF 韌體內建 800／1000 ms 冷卻，會在毫秒級間隔下自行擋掉指令，量到的是節流而不是掉包。
- Unity 的 `Update` 一格約 16 ms，無法產生 0／1／5／10 ms 的間隔；9600 baud 邊送邊印也會把間隔偷偷拉長。
- 沒有逐筆紀錄，也沒有地方記錄面板讀數，無法把「送了幾次」和「跑步機變了多少」對起來。
- 測試共 72 輪、每輪 40～120 筆，研究人員要站在跑步機旁讀面板、同時操作電腦；介面若繁瑣，容易輸錯數字、跳錯步驟或忘記存檔。

## Solution

一套 Unity 測試工具加兩支 Arduino 測試韌體：

- 研究人員在 Unity 裡選入口與 COM port，按一下就能依序跑完整個條件矩陣（4 種間隔 × 3 種次數 × 3 輪），或單獨跑一輪。
- 毫秒級間隔由 Arduino 自己用 `micros()` 執行；Unity 只下「這一段送 20 筆、方向、間隔」的指令，並在每段結束後收回整段時間戳。
- 介面以「下一步該做什麼」為中心：畫面永遠只突出一個主要動作，提示目前應看到的面板速度，研究人員輸入面板讀數後按 Enter 即繼續。
- 每段、每輪的結果即時寫入 CSV，可直接用 Excel 開啟整理成論文表格；推算的掉包數在介面上即時顯示。

## User Stories

### 連線與準備

1. 身為研究人員，我想從下拉選單選 COM port，而不是手打名稱，這樣不會因為打錯 port 而連不上。
2. 身為研究人員，我想按「重新整理」就能看到目前插著的所有 COM port，這樣換了 USB 孔也能馬上找到 Nano。
3. 身為研究人員，我想選擇入口是「RF」或「光耦」，這樣同一個介面能測兩套硬體。
4. 身為研究人員，我想在連線後看到明顯的綠／紅狀態燈與韌體回報的入口類型，這樣能確認插的是對的那塊板子。
5. 身為研究人員，若選的入口和韌體回報的入口不一致，我想看到警告並無法開始測試，這樣不會把 RF 的資料記成光耦。
6. 身為研究人員，我想要連線失敗時看到中文原因（被占用、找不到 port、逾時），這樣知道要關 Arduino IDE 序列埠監控還是換線。
7. 身為研究人員，我想要上次用的 port、入口與受測者／備註欄位被記住，這樣每次開啟不用重新設定。

### 選擇測試

8. 身為研究人員，我想看到 4 × 3 的條件矩陣（間隔 × 次數），每格顯示已完成幾輪／應完成幾輪，這樣一眼就知道還缺哪些。
9. 身為研究人員，我想按「自動跑下一輪」由系統挑下一個未完成的條件，並依規則讓 RF／光耦交替先做，這樣不必自己排順序。
10. 身為研究人員，我想點矩陣上任一格單獨跑一輪，這樣可以補做或重做特定條件。
11. 身為研究人員，我想在開始前看到這一輪的摘要（入口、間隔、次數、段數、預計速度範圍），這樣確認無誤再按開始。
12. 身為研究人員，我想可以修改重複輪數與每段筆數，這樣前測後能調整而不用改程式。
13. 身為研究人員，我想把一輪標記為「作廢」並註明原因，這樣出狀況的輪次不會混進統計，但原始資料仍保留。

### 執行一輪

14. 身為研究人員，我想按一次「開始」後系統自動送啟動、倒數 5 秒，這樣跑帶穩定前不會送出調速指令。
15. 身為研究人員，我想看到預熱進度（第幾次／應送幾次），這樣知道系統正在把速度帶到起點。跑步機開機即為 1.0 km/h，與起點相同時預熱為 0 次。
16. 身為研究人員，預熱完成後我想看到「請輸入面板速度（預期 1.0）」的大字提示，這樣知道現在要看面板。
17. 身為研究人員，我想直接用鍵盤輸入數字並按 Enter 確認，不用移滑鼠點按鈕，這樣能一手扶跑步機一手打字。
18. 身為研究人員，我想輸入框接受 `1`、`1.0`、`10`（自動視為 1.0）等寫法，並拒絕超出 0～12 的值，這樣減少手誤。
19. 身為研究人員，若輸入的預熱速度不是 1.0，我想被詢問「重新預熱」或「以此速度為起點繼續」，這樣起點錯誤不會汙染整輪。
20. 身為研究人員，我想在每段執行時看到「段 3／6，加速 20 筆，間隔 5 ms」與進度條，這樣知道系統在做什麼。
21. 身為研究人員，每段結束時我想看到「預期面板速度 3.0」並輸入實際讀數，這樣能逐段核對。
22. 身為研究人員，我想在輸入後立即看到該段推算的掉包數，這樣當場就能決定要不要錄影存證或重做。
23. 身為研究人員，若某段推算終點會低於 0.1 或高於 12，我想看到「可能觸底／觸頂，無法判讀」標記，這樣不會把被吃掉的指令誤算成掉包。
24. 身為研究人員，若 Arduino 回傳筆數少於 20 或逾時沒有 `DONE`，我想看到明確警告並寫入紀錄，這樣能區分序列埠問題與跑步機問題。
25. 身為研究人員，我想在任何時候按下大紅色「緊急停止」（也可用空白鍵），系統立刻要求 Arduino 中斷迴圈並送停止，這樣跑步機異常時能馬上停下。
26. 身為研究人員，我想在輸入面板速度前可以「撤銷上一次輸入」，這樣打錯能修正。
27. 身為研究人員，一輪結束時我想看到這輪的總結（各段掉包數、總掉包、Arduino 實際間隔平均／最大），這樣能確認資料合理。
28. 身為研究人員，我想在一輪結束後系統自動送停止，並提示「確認跑帶已停止後再開始下一輪」，這樣不會在跑帶仍在轉時接著測。

### 紀錄與匯出

29. 身為研究人員，我想每段結束就寫入 CSV，而不是整輪結束才寫，這樣 Unity 當掉也不會遺失已完成的段。
30. 身為研究人員，我想要逐筆 CSV 包含輪次、入口、間隔、總次數、段號、序號、方向、Arduino 輸出開始／結束時間（µs）與實際間隔，這樣能分析韌體是否確實照間隔送出。
31. 身為研究人員，我想要每段 CSV 包含預期變化、面板起點／終點、推算掉包數、觸底／觸頂旗標、回報筆數不足旗標、作廢標記與備註，這樣能直接整理成第五章表格。
32. 身為研究人員，我想要一份每輪摘要 CSV（每輪一列），這樣在 Excel 做樞紐分析時不必自己彙總。
33. 身為研究人員，我想在介面上按「開啟紀錄資料夾」，這樣不用自己找檔案路徑。
34. 身為研究人員，我想要 CSV 用 UTF-8 BOM 輸出，這樣 Excel 直接開中文不會亂碼。
35. 身為研究人員，重新開啟 Unity 時我想讓矩陣進度從既有 CSV 還原，這樣測試可以分好幾天做完。
36. 身為研究人員，我想在每輪紀錄中看到韌體版本與單筆動作參數（光耦按壓時間、RF 重送次數與釋放時間），這樣論文能交代測試配置。

### 韌體端

37. 身為研究人員，我想讓兩支韌體開機時回報入口類型、版本與參數，這樣 Unity 能自動驗證並記錄。
38. 身為研究人員，我想讓韌體在執行一段時完全不輸出序列資料，這樣間隔不被序列傳輸拉長。
39. 身為研究人員，我想讓韌體在收到中止指令時立刻停止迴圈，這樣緊急停止不必等整段跑完。
40. 身為研究人員，我想讓韌體保留「單發」指令（啟動、停止、單次加減速），這樣預熱與手動測試可以共用同一支韌體。
41. 身為研究人員，我想讓光耦韌體在任何結束路徑（完成、中止、錯誤）都把所有腳位拉回 LOW，這樣不會有按鍵卡住。

## Implementation Decisions

### 架構與模組

- **測試核心（純 C#，不依賴 UnityEngine）**：負責一輪的狀態機、測試計畫生成、協定解析與段結果計算。這是唯一需要深度測試的模組，對外只暴露：
  - 產生計畫：輸入（入口、間隔、總次數、每段筆數、起點速度、步進），輸出段列表（方向、筆數、預期起點／終點速度）。
  - 狀態推進：餵入「Arduino 回傳的一行」或「研究人員輸入的面板速度」或「使用者動作（開始／中止／撤銷）」，回傳目前狀態與要送出的指令行。
  - 段評估：輸入預期與實際起點／終點速度與回報筆數，輸出推算掉包數與旗標。
- **序列連線介面**：抽象成「送一行／收到一行／連線狀態」的介面；正式實作包 `System.IO.Ports.SerialPort`，在背景執行緒讀取並以執行緒安全佇列交給主執行緒。測試用假 Arduino 實作同一介面。
- **紀錄器**：把核心產出的逐筆／每段／每輪結果寫成 CSV（每段結束即 flush），並能從既有 CSV 還原矩陣進度。
- **介面元件（MonoBehaviour + OnGUI）**：只負責呈現核心狀態與轉發使用者輸入，不含判定邏輯。
- 不依賴、不修改既有的 `TreadmillController` 與 `RfSenderSerialController`。

### 一輪的狀態機

```
Idle → Connecting → Ready
Ready → Starting (送 START，倒數 5 s)
      → WarmingUp (單發補足開機速度與起點的差額，間隔 1 s；開機 1.0、起點 2.0 時為 10 次)
      → AwaitWarmupReading (輸入面板速度，預期 1.0)
      → RunningSegment(k) (送 RUN，等 20 筆時間戳 + DONE)
      → AwaitSegmentReading(k)
      → …重複至所有段完成…
      → Stopping (送 STOP) → RoundSummary → Ready
任何狀態 + 緊急停止 → Aborting (送 ABORT，再送 STOP) → RoundSummary(作廢)
```

### 序列協定（115200 baud，每行以 `\n` 結尾）

Unity → Arduino：

| 指令 | 意義 |
|---|---|
| `HELLO` | 要求韌體回報身分 |
| `ONE,<cmd>` | 單發：`START`／`UP`／`DOWN`／`STOP` |
| `RUN,<UP\|DOWN>,<n>,<gap_ms>` | 連續送 n 筆，每筆輸出完成後休息 gap_ms 再送下一筆 |
| `ABORT` | 立即中止目前迴圈 |

Arduino → Unity：

| 回應 | 意義 |
|---|---|
| `READY,<RF\|OPTO>,<fw_version>,<param=value;…>` | 開機或回應 HELLO |
| `ACK,<原指令>` | 已接受指令 |
| `T,<i>,<start_us>,<end_us>` | 第 i 筆輸出的開始／結束時間（整段結束後才一次送出） |
| `DONE,<n_sent>` | 一段完成，實際輸出筆數 |
| `ABORTED,<n_sent>` | 已中止 |
| `ERR,<原因>` | 指令格式錯誤或忙碌中 |

- 韌體在 `RUN` 迴圈中僅以非阻塞方式檢查是否收到 `ABORT`，不做任何輸出。
- 時間戳存放於 RAM（每段上限 20 筆，可設定，但需受 Nano 2 KB RAM 限制）。

### 韌體單筆動作（沿用正式版，寫成常數並在 READY 中回報）

- **光耦**：腳位 3 加速、4 減速、5 停止、6 啟動；按壓 HIGH 120 ms 後 LOW。
- **RF**：四組 24 bit 代碼不變、`setRepeatTransmit(2)`；每筆發送後保留 250 ms 釋放時間。移除 800／1000 ms 冷卻、RF 接收功能與其 20／50 ms 延遲。
- 「休息間隔」指上一筆單筆動作完成後到下一筆開始的時間。

### 判定規則

- 每段推算掉包數 = |預期速度變化 − 面板實際變化| ÷ 0.1，四捨五入為整數。
- 面板實際變化以「該段起點讀數（上一段終點）」到「該段終點讀數」計算，不以理論值為起點，避免誤差累積。
- 若以實際起點加上預期變化會超出 1.0～12.0（跑步機最低速度 1.0），標記「可能觸底／觸頂」。
- `DONE` 回報筆數小於應送筆數、或逾時未收到 `DONE`，標記「Arduino 回報不足」。
- 段逾時 = 應送筆數 ×（單筆動作時間 + 間隔）× 2 + 2 s。

### 易於操作的介面原則

- 畫面分三區：上方狀態列（連線燈、入口、目前輪次與條件）、中央「現在要做的事」大卡片（單一主要按鈕或數字輸入框＋預期值）、右側條件矩陣與進度。
- 任何時刻只有一個主要動作被強調；不可用的按鈕停用而非隱藏。
- 面板速度輸入框在需要時自動取得焦點，Enter 確認、Esc 撤銷上一次輸入。
- 空白鍵與紅色按鈕皆為緊急停止，任何狀態可用。
- 文字全為繁體中文，字級放大以便站在跑步機旁閱讀。
- 偏好設定（port、入口、輪數、備註）以 PlayerPrefs 保存。

### 專案設定

- API Compatibility Level 改為 .NET Framework（`System.IO.Ports` 所需）。
- Active Input Handling 改為 Both；介面以 OnGUI 事件處理鍵盤，不使用舊版 `Input` API。
- 新增一個獨立測試場景，只含測試工具元件。

### 紀錄輸出

- 位置：專案根目錄下的紀錄資料夾，每次 Unity 執行產生一組以時間戳命名的檔案：逐筆、每段、每輪摘要三份 CSV，UTF-8 BOM。
- 每輪摘要列含：輪次 ID、日期時間、入口、韌體版本與參數、間隔、總次數、段數、總掉包、各旗標、作廢與原因、備註。

## Testing Decisions

- **唯一測試接縫：序列連線介面。** 以 C# 假 Arduino 實作同一個「送一行／收一行」介面，可設定：正常回應、少回筆數、逾時不回 DONE、回報錯誤入口、回傳 ERR、中止時行為。測試只透過這個接縫與使用者動作驅動測試核心，斷言對外行為（送出的指令行、狀態、段結果、CSV 列內容），不檢查內部欄位。
- **受測模組**：
  - 測試核心：計畫生成（40／80／120 → 2／4／6 段、方向交替、預期速度 2.0↔4.0）、完整一輪的狀態流程、緊急停止、撤銷輸入、入口不符阻擋、各旗標判定與掉包數計算。
  - 紀錄器：給定一輪結果寫出的 CSV 列與欄位、從 CSV 還原矩陣進度。
- **測試框架**：Unity Test Framework 的 EditMode 測試（套件已在相依鎖檔中，需在 manifest 明確加入）。測試核心不依賴 UnityEngine，故也可在一般 NUnit 下執行。
- **既有前例**：專案內目前沒有任何測試；此為第一批。
- **韌體**：不寫自動化測試。以台架驗收清單人工確認：開機 READY 內容、`RUN` 在 0 ms 間隔下的時間戳間距、`ABORT` 能在一筆內中止、光耦結束後腳位全為 LOW（以 LED 或三用電表確認）。
- **硬體實機**：以一輪 40 筆、10 ms 間隔做前測，確認面板讀數流程與 CSV 內容後才開始正式矩陣。

## Out of Scope

- 研究問題二：外部原廠遙控器監聽與 Arduino 辨識率測試。
- 多台電腦同時控制同一台跑步機的干擾測試。
- 實際帶速量測（轉速計、Hall 感測器）與面板影片的自動辨識。
- RF 參考接收器（第二塊 Arduino）自動確認空中訊號。
- 修改或整合既有遊戲用的 `TreadmillController`、`RfSenderSerialController`、MediaPipe 流程。
- 統計分析與論文圖表產生（僅輸出可供 Excel 使用的 CSV）。

## Further Notes

- 硬體：Arduino Nano V3.0（ATmega328P）、XTERRA DT168（0～12 km/h，每次按鍵 0.1 km/h，開機速度與最低速度皆為 1.0 km/h）。計分起點 2.0 km/h，預熱 10 次，各段 2.0↔4.0。
- 每輪會記錄預計與實際送出的加速、減速次數（40 次＝加速 20、減速 20），顯示在畫面並寫入每輪 CSV。
- 測試期間跑帶上不站人；原廠停止鍵保持可用。
- 需寫入論文的限制：同一段內「漏一筆」與「多一筆」會互相抵銷而無法從面板讀數分辨；跑步機層的判定只到段的層級，逐筆核對需仰賴錄影。
- 本專案目前不是 git 儲存庫，也未設定 issue tracker，故本規格以檔案形式存放。
