# 實驗設計

> 版本：2026-11-27。
> 這份文件說明實驗要做什麼、怎麼做、怎麼看結果。程式和資料欄位的細節在 [README](../README.md)。
> 目前沒有任何實機結果。文中的時間數字都是推算值。

## 1. 這個實驗在做什麼

電腦叫跑步機加速或減速很多次。我們比對兩個數字：**送了幾次**，以及**跑步機動了幾格**。如果少了，就查是在哪裡少的。

要回答兩個問題：

1. **掉多少？** 用光耦和 RF 控制跑步機，各有多少指令沒有作用？
2. **掉在哪裡、為什麼？** 指令是在哪一段不見的？

這是機器對機器的測試，**沒有受試者**。研究人員只負責按開始、看面板、記下異常。跑帶上不站人。

## 2. 名詞

| 名詞 | 意思 |
|---|---|
| 指令 | 一次加速或一次減速。成功時速度變化 0.1 km/h（一格） |
| 入口 | 控制跑步機的方式。**光耦**（V1，代替手指按面板）或 **RF**（V2，代替遙控器） |
| 送法 | 電腦用什麼節奏送指令。有 A、B、C 三種，另有 RUN 對照 |
| gap | A 送法和 RUN 對照中，兩個指令之間設定的等待時間 |
| n | 一段裡的指令數：30、60 或 90 |
| 段 | 同一方向連續送 n 個指令 |
| 輪 | 4 段：加速、減速、加速、減速 |
| 掉包 | 送出的指令沒有反映在跑步機上 |

## 3. 指令走過哪裡，怎麼知道掉在哪

```
①電腦  ──USB──▶  ②③Arduino  ──▶  ④光耦／RF 模組  ──▶  ⑤跑步機
```

| 檢查點 | 要問的問題 | 現在量得到嗎 |
|---|---|---|
| ① | 電腦送了幾個？ | 可以（A 送法） |
| ② | Arduino 收到幾個？ | 可以（A 送法） |
| ③ | Arduino 做了幾個？ | 可以 |
| ④ | 光耦或 RF 有沒有真的送出訊號？ | **不行**，缺量測硬體 |
| ⑤ | 跑步機動了幾格？ | 可以，但每段只能看一次面板 |

相鄰兩個數字相減，就知道少在哪裡：

| 畫面上的名稱 | 算法 | CSV 欄位 |
|---|---|---|
| 序列端少 | 電腦送出 − Arduino 收到 | `link_lost` |
| 跑步機端少 | Arduino 做了 − 面板動的格數 | `treadmill_missing` |

**例子**：電腦送 30，Arduino 收到 29、做了 29，面板動 27 格。結果是序列端少 1，跑步機端少 2。

兩個注意事項：

- 「跑步機端少」是**負數**時，表示跑步機動得比指令多。
- 因為量不到 ④，「跑步機端少」分不出是**模組沒送出訊號**，還是**跑步機沒收下**。

## 4. 三種送法

| 送法 | 怎麼送 | 回答什麼 | 狀態 |
|---|---|---|---|
| **A 等回覆** | 電腦送一個，等 Arduino 回「做完了」，停 gap，再送下一個 | 指令不塞車時，會不會掉？掉在哪？ | 程式完成，**還沒實機測** |
| **B 固定間隔** | 電腦每隔固定時間送一個，不等回覆 | 送多快開始掉？ | 還沒做 |
| **C 原版重現** | 電腦約每秒送一個，Arduino 照原版系統的方式處理 | 原本遇到的掉包是怎麼來的？ | 還沒做 |
| **RUN 對照** | 電腦只說一次「做 n 個」，Arduino 自己連續做 | 拿掉逐個傳送後，表現如何？ | 程式完成，**還沒實機測** |

### A 送法要注意

- 「做完了」只代表 Arduino 做完動作。它**不代表**跑步機收到。
- 電腦**不重送**沒有回覆的指令。重送會改變次數。
- **實際停的時間比 gap 長。** 實際時間 ＝ 回覆傳回電腦 ＋ 電腦處理 ＋ gap ＋ 下一個指令傳過去。
- 多出來的時間可能有幾毫秒到十幾毫秒（還沒量）。這可能蓋掉 0、1、5、10 ms 的差別。
- 論文要寫**量到的時間**（`gap_us`），不能只寫設定值。
- 正式測試前先做第 9 節的 T2。分不出差別時，改用較大的 gap（例如 0／50／100／200 ms），或用 RUN 對照比較短 gap。**開始正式測試後不再改。**

收送的細部規則（逾時、壞掉的指令、重開機）見 [README 的 A 送法收送規則](../README.md#a-送法的收送規則)。

### B 送法的打算

- 間隔暫定 1000、500、350、150、100、10 ms。
- 光耦做一個指令約 120 ms，RF 約 340 ms。送得比這更快，指令會在 Arduino 裡排隊，排滿就掉。
- 排滿會掉是預料中的事。要看的是：掉包是否只發生在序列端，跑步機端有沒有另外掉。

### C 送法的打算

- RF 原版：指令太密時 Arduino 直接略過（800 ms 和 1000 ms 的冷卻）；排隊中的指令會被清掉；電腦不看回覆。
- 光耦原版：沒有冷卻；指令排隊時，按鍵幾乎沒有放開的時間。
- 傳輸速度用原版的 9600。
- Arduino 每略過一個指令，要記下原因。
- 手上沒有光耦版的感測控制程式，所以它原本的送出節奏無法確認。

## 5. 測哪些條件

A 送法的條件：

| 項目 | 內容 | 數量 |
|---|---|---|
| 入口 | 光耦、RF | 2 |
| gap | 0、1、5、10 ms | 4 |
| n | 30、60、90 | 3 |
| 每個條件重複 | 3 輪 | 3 |
| **合計** | | **72 輪** |

整個過程保持不變：跑步機、Arduino、接線、RF 天線位置和距離（拍照記下）、起點速度 2.0 km/h、單個指令的動作方式。

其他送法的輪數：RUN 對照 72 輪（選做）、B 暫定 36 輪、C 暫定 10 輪。

- 工具會排順序，光耦和 RF 輪流先做。
- 工具**沒有打亂** gap 和 n 的順序。電池、溫度、干擾可能隨時間改變，分析時要看每輪的時間。
- 時間不夠時，先不做 RUN 對照，再不做 n＝60。論文要寫明省了什麼、為什麼。

## 6. 一輪怎麼做

1. 程式啟動跑步機，等 5 秒。
2. 程式按 11 次加速，讓速度到 2.0。這段不算分。
3. 你確認面板是 2.0。
4. 程式依序跑 4 段。
5. 每段結束，等面板數字不再變，輸入讀數。
6. 程式停止跑步機。你看總結。

全程錄影，要同時拍到跑步機面板和電腦螢幕。

**什麼時候作廢一輪**：有人碰到跑步機、看錯面板、Arduino 重開機、出現「可能觸底／觸頂」。
**指令遺失或沒回覆不要作廢**，那是要收集的資料。
作廢的輪次不算掉包率，但紀錄保留，查原因時用。

## 7. 看到結果怎麼判斷

| 看到什麼 | 少在哪裡 | 接著查什麼 |
|---|---|---|
| 序列端少大於 0，或有壞掉的指令（`rejected`、`arduino_bad`） | 電腦到 Arduino | USB 線、傳輸速度、有沒有別的程式占用序列埠 |
| 有指令沒回覆（`no_reply`），但序列端沒少 | 回覆的路上 | 回覆太慢或遺失 |
| Arduino 重開機（`rebooted`） | Arduino | 供電是否穩定 |
| 跑步機端少大於 0，序列端沒少 | 模組或跑步機 | 量 ④；比較不同 gap；看錄影是否只動了幾格（被當成長按） |
| 跑步機端少小於 0 | 跑步機多動 | 長按自動連續調速；RF 一個指令被算兩次 |
| 每次固定少 1，而且是第一個 | 第一個指令 | 剛啟動或閒置後，第一下是否沒作用 |
| 可能觸底／觸頂（`possibly_clamped`） | 無法判斷 | 這段的跑步機端數字不能用 |

「少在哪裡」可以從資料看出來。「接著查什麼」只是**可能的原因**，驗證前不能當結論。

## 8. 整理數據的規則

1. 只用完成的輪次（`status = completed`）。
2. 一段算一筆資料。同一段的指令常常一起失敗，不能當成互相獨立的次數。
3. 算比例時，分母要對：
   - 序列端少 ÷ 電腦送出（`pc_sent`）
   - 跑步機端少 ÷ Arduino 做了（`arduino_executed`；RUN 對照用 `reported_count`）
4. 「推算掉包」（`drops`）是用**預定的 n** 算的。段提早結束時，沒送出的指令也算在內。只有送滿 n 個的段才能用它。
5. 觸底或觸頂的段：跑步機端數字不用，序列端數字照用。
6. 分條件列出，不要把全部輪次併成一個成功率。
7. 比較光耦和 RF 時，同時寫出實際送出速度。兩者做一個指令的時間不同。
8. 每個條件只有 3 輪，只看得出大差別。沒看到掉包，不能寫「不會掉」。

欄位說明見 [README 的紀錄檔](../README.md#紀錄檔csv)。

## 9. 正式開始前要先試

| 編號 | 做什麼 | 要知道什麼 |
|---|---|---|
| T1 | 照[台架清單](BenchAcceptance.md) B、C 節檢查板子和連線 | 韌體能不能用 |
| T2 | A 送法 n＝30，gap 0 和 10 各跑一輪，比較 `commands` 檔的 `gap_us` | 不同 gap 分不分得出來 |
| T3 | 用手按住面板鍵、遙控器鍵 0.5、1、3、5 秒 | 按多久會變成連續調速 |
| T4 | 手動段每秒送一個，光耦和 RF 各 60 個，看錄影逐個核對 | 慢慢送時會不會掉 |
| T5 | 停 30 秒後送一個，加速、減速各 10 次 | 閒置後第一下是否沒作用 |
| T6 | 手動段選 RUN 對照，gap 0、10、100 ms、1 s 各跑 n＝30 | 光耦放開太短時，會不會被當成長按 |

速度上限 12 km/h 已確認（2026-11-27）。這些項目的依據見[研究筆記](research/burst-stress-test-design.md)。

## 10. 限制與還沒決定的事

**做不到的事**

- 面板只能每段看一次。同一段裡少一個又多一個，會互相抵銷。
- 量不到 ④，所以分不出模組和跑步機的責任。
- 面板顯示的是設定速度，不是跑帶的實際速度。
- 只有一台跑步機和一套板子，結果不能推到其他機器。
- A、B 和 RUN 用的是測試韌體。原版系統的行為要靠 C 回答。

**還沒決定**

- 有沒有第二塊 Nano 加 RF 接收模組、邏輯分析儀，可以量 ④。接收器自己也可能漏收，用之前要先校正。
- 時程能否延後（原訂 2026-11-27 做完實驗）。
- gap 要不要加大（看 T2）。
- B 的間隔和 C 的節奏，做之前再確認。
