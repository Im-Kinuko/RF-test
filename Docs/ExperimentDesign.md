# 實驗設計：跑步機調速指令的掉包位置與原因

> 版本：2026-11-27。取代 [StressTest-Spec.md](StressTest-Spec.md) 中「由 Arduino 連續送出整段指令」的主實驗設計；該送法保留為對照組（`RUN`）。
> 實作狀態見[第 11 節](#11-實作狀態)。本文所有時序數字在台架驗收前都是推算值。

## 1. 目的

比較兩個跑步機控制入口 V1（光耦）與 V2（433 MHz RF），回答兩個問題：

1. **掉多少**：在相同的加減速指令與不同發送間隔下，電腦送出的調速指令有多少沒有反映在跑步機上？
2. **掉在哪裡、為什麼**：掉包發生在「電腦 → Arduino → 控制入口 → 跑步機」的哪一段，可能原因是什麼？

這是台架上的系統測試，**沒有受試者**。指令由電腦產生；研究人員只負責啟停、讀面板、記錄異常。跑帶上不站人。

## 2. 受測鏈路與檢查點

```
電腦 (Unity) ──USB 序列──▶ Arduino Nano ──▶ 光耦／RF 模組 ──▶ 跑步機 (XTERRA DT168)
      ①                       ②③                  ④                    ⑤
```

| 檢查點 | 觀察什麼 | 怎麼量 | 目前能否量到 |
|---|---|---|---|
| ① 電腦送出 | 每筆序號與送出時間 | 測試工具記錄 | 可 |
| ② Arduino 收到 | 通過檢查碼的指令數、毀損行數、收到時間 | 韌體計數器與回覆 | 可（A 送法） |
| ③ Arduino 執行 | 執行的指令數、動作起訖時間 | 韌體計數器與回覆 | 可 |
| ④ 控制入口輸出 | 光耦輸出端是否導通又放開；空中是否有 RF 訊號 | 邏輯分析儀／示波器；第二塊 Nano 加 433 MHz 接收模組 | **不可**（硬體未備） |
| ⑤ 跑步機接受 | 面板速度變化 | 研究人員輸入面板讀數，全程錄影 | 可，但只到段的層級 |

### 各段的掉包定義

以「一段」（同方向連續 n 筆）為單位：

| 指標 | 公式 | 意義 |
|---|---|---|
| `link_lost` | ① 送出數 − ② 收到數 | 電腦到 Arduino 掉的筆數 |
| 未執行 | ② 收到數 − ③ 執行數 | Arduino 收到卻沒執行（冷卻、忙碌） |
| `panel_steps` | 面板往指令方向移動的格數（0.1 km/h 一格） | 跑步機實際反應的次數（淨值） |
| `treadmill_missing` | ③ 執行數 − `panel_steps` | Arduino 之後掉的筆數；**負值代表多反應** |

分母要和指標對應：`link_lost` 除以電腦送出數（`pc_sent`），`treadmill_missing` 除以執行數（`arduino_executed`）。

另外保留 `drops`＝|預期變化 − 面板實際變化| ÷ 0.1，預期變化以**計畫的 n** 計算。段提早結束（逾時、重開機）時，沒送出的指令也會算進 `drops`；只有 `pc_sent`＝n 的段，`drops` 才能當掉包指標。

④ 沒有量測時，`treadmill_missing` 合併了「入口沒有正確輸出」與「跑步機沒有接受」兩種情況，**不能**單獨歸因給任一方。

## 4. 送法

三種送法的差別在「下一筆什麼時候送」與「Arduino 遇到指令時怎麼處理」。

| 送法 | 誰決定節奏 | 下一筆的時機 | Arduino 行為 | 回答什麼 |
|---|---|---|---|---|
| **A 等回覆** | 電腦 | 收到完成回覆後再等 gap | 逐筆執行、逐筆回覆 | 沒有排隊問題時，鏈路、入口、跑步機會不會掉 |
| **B 固定間隔** | 電腦 | 每隔固定時間送，不等回覆 | 逐筆執行、逐筆回覆 | 送多快開始掉、掉在哪一段 |
| **C 原版重現** | 電腦 | 照原版遊戲節奏（約每秒 1 筆） | 原版行為：冷卻、清空緩衝 | 原版系統的掉包能否重現、原因是什麼 |
| `RUN` 對照 | Arduino | 上一筆動作完成後等 gap | 一次收到整段指令後自行連續送 | 排除序列傳輸後，Arduino 之後的鏈路表現 |

### 4.1 A 送法（先實作）

```
電腦                                   Arduino
ZERO                              ──▶  計數器歸零
                                  ◀──  ACK,ZERO
CMD,17,UP*CK                      ──▶  收到（記 rx_us）→ 按壓／發射（記 start_us、end_us）
                                  ◀──  X,17,rx_us,start_us,end_us*CK     ← 完成回覆
（等 gap）
CMD,18,UP*CK                      ──▶  …
…共 n 筆…
STAT                              ──▶
                                  ◀──  STAT,收到數,執行數,毀損數*CK
```

- **完成回覆**只代表 Arduino 做完動作（光耦腳位放開；RF 發射並等完 250 ms）。它不代表入口有輸出，也不代表跑步機收到。
- **檢查碼**：`*` 之前所有位元組做 XOR，寫成兩位大寫十六進位。雙向都檢查。
- **序號**：連線期間一直遞增，不重複使用，遲到的回覆不會配錯。逾時後才到、但這段還沒結束的回覆記為 `late`。
- **指令不重送**。重送會改變指令次數，量到的就不是原始掉包。`ZERO` 和 `STAT` 不影響跑步機，沒有回覆時最多問 3 次。`ZERO` 沒有確認、或 `STAT` 問不到時，該段的 Arduino 計數留空。
- **逾時**：送出後超過「2 × 單筆動作時間 + 1 秒」沒有回覆，記為 `no_reply`，繼續下一筆；連續 3 筆沒有準時回覆就結束這一段（遲到的回覆不會讓計數歸零）。
- Arduino 回報行毀損時回 `NAK`（不認得的行回 `ERR`），該筆記為 `rejected`，至少等 50 ms 再送下一筆，避免同一行造成的第二個錯誤算到下一筆。`NAK` 不帶序號，所以歸屬到「當時正在等回覆的那一筆」。
- 段執行中 Arduino 重新開機（收到 `READY`）時結束這一段，標記 `rebooted`；等讀數時重開機同樣標記。
- `STAT` 的收到數或執行數比電腦收到的完成回覆還少時，代表計數中途歸零過（例如重開機但 `READY` 遺失），該段計數留空。反過來，重開機發生在沒有任何回覆之前就偵測不到。
- 電腦端用獨立執行緒收送，不受畫面更新率限制。

**A 的 gap 不等於實際休息時間。** 兩筆動作之間的實際空檔是：

> 回覆傳回電腦 ＋ 電腦處理 ＋ gap ＋ 下一筆傳到 Arduino

序列傳輸加 USB 轉換晶片的延遲可能有數毫秒到十幾毫秒（依晶片而定，尚未實測）。因此：

- 論文一律報告 Arduino 量到的實際空檔（`gap_us`），`gap_ms` 只是設定值。
- 前測要比較四個 gap 的 `gap_us` 分布。若四組分布重疊，擇一處理：拉大級距（例如 0／50／100／200 ms），或把短間隔的比較交給 `RUN` 對照組。**開始正式矩陣前定案，之後不改。**

### 4.2 B 送法（尚未實作）

- 電腦每隔 T 送一筆，不等回覆。暫定 T＝1000／500／350／150／100／10 ms，跨過光耦（120 ms）與 RF（約 340 ms）的單筆動作時間。
- T 小於單筆動作時間時，指令會在 Arduino 的 64 bytes 接收緩衝排隊，滿了就遺失。這是可以事先預期的結果；要確認的是掉包是否只發生在 ②（`link_lost`），以及 ⑤ 是否另外有掉包。
- 紀錄格式、檢查碼、計數器沿用 A。

### 4.3 C 送法（尚未實作）

- 重現原版 V1、V2 韌體的指令處理，再加上計數與回覆。原版行為：
  - V2（RF）：全域冷卻 800 ms、同指令冷卻 1000 ms，冷卻中略過；每次讀一個字元後清空接收緩衝。原版電腦端寫入成功就當作送達，不看回覆。
  - V1（光耦）：沒有冷卻，也沒有放開時間；指令排隊時兩次按壓緊接著發生。
- 鮑率 9600，節奏照原版電腦端（約每秒 1 筆）。
- 每筆略過要記原因（冷卻、被清掉）。
- 限制：目前取得的原版程式中沒有 V1 的感測控制端，V1 原本的指令節奏無法確認。

## 5. 條件矩陣與執行順序

| 送法 | 條件 | 每條件輪數 | 輪數 |
|---|---|---|---|
| A | 2 入口 × 4 gap × 3 n | 3 | 72 |
| `RUN` 對照（選做） | 2 入口 × 4 gap × 3 n | 3 | 72 |
| B（暫定） | 2 入口 × 6 間隔 × n＝30 | 3 | 36 |
| C（暫定） | 2 入口 × n＝30 | 5 | 10 |

- 每個送法各自記進度；工具依「間隔 → n」排程，每條件中光耦與 RF 的先後逐輪交替。
- 工具目前**沒有隨機化**間隔與 n 的順序。時間相關的變化（電池、溫度、無線干擾）可能和條件混在一起；每輪的時間有記錄，分析時要檢查。
- 時程不足時依序縮減：先拿掉 `RUN` 對照，再把 A 的 n 減為只跑 30 與 90。縮減方式與理由要寫進論文。

## 6. 一輪的程序

1. 送出啟動，倒數 5 秒。
2. 預熱 11 次單發加速（間隔 1 秒），面板應停在 2.0。不計分。
3. 研究人員確認面板為 2.0。
4. 依序跑 4 段：加速 n、減速 n、加速 n、減速 n。
5. 每段結束後等面板數字停止變化，輸入讀數並確認。下一段以實際讀數為起點。
6. 送出停止，檢視總結；有異常（有人碰觸、看錯面板、設備重開機）就作廢並寫原因。A 送法的指令遺失、毀損、沒回覆**不是**作廢理由。作廢輪次不列入掉包率，但紀錄保留，供原因分析。

全程錄影，畫面同時拍到跑步機面板與電腦螢幕。

## 7. 掉包原因判讀

| 觀察到 | 代表 | 下一步查什麼 |
|---|---|---|
| `link_lost` > 0 或 `arduino_bad` > 0 | 電腦到 Arduino 掉包或毀損 | USB 線、鮑率、接收緩衝溢位、同一時間是否有其他程式用序列埠 |
| `rejected` > 0 | 指令送到時內容壞掉 | 同上 |
| `no_reply` > 0 但 `link_lost` ＝ 0 | 指令有執行，回覆沒回來或太慢 | 回覆路徑、逾時設定 |
| `rebooted` ＝ 1 | Arduino 執行中重開機 | 供電、按壓或發射時的電壓下降 |
| C 送法出現「收到卻沒執行」 | 韌體邏輯丟掉 | 略過原因（冷卻、清緩衝） |
| `treadmill_missing` > 0，前兩段為 0 | 問題在入口輸出或跑步機 | 補量 ④；比較不同間隔；看錄影是否整串只動幾格（長按或合併） |
| `treadmill_missing` < 0 | 多反應 | 長按自動連續調速、RF 重複幀被算成多次 |
| 固定少 1 且總在第一筆 | 啟動或閒置後第一下無效 | 台架驗收 D 節 |
| `possibly_clamped` ＝ 1 | 撞到速度上下限 | 該段的跑步機端指標不可用 |

「代表」欄是由資料能直接推得的位置；「下一步」是待驗證的假設，不能直接當結論。

## 8. 資料與分析

欄位定義見 [README 的紀錄檔一節](../README.md#紀錄檔csv)。

1. 只分析 `status = completed` 的輪次。
2. 觀察單位是**段**。同一段內的指令不能當成獨立試驗（長按、緩衝溢位會讓失敗成串）。
3. 逐段列出 `link_lost`（分母 `pc_sent`）與 `treadmill_missing`（分母 `arduino_executed`），依送法、入口、gap、n、方向分組；不要把所有輪次合併成一個成功率。`RUN` 對照沒有這些電腦端欄位，用 `treadmill_missing`（分母 `reported_count`）。
4. `possibly_clamped`＝1 的段排除跑步機端指標，但**保留**鏈路端指標（`link_lost`、`rejected`、`no_reply`）。
5. A 送法中 `report_short`＝1 是結果（有指令沒有完成往返），不是排除條件。
6. 兩個入口的 gap 定義相同，但單筆動作時間不同（120 ms 與約 340 ms），RF 另含固定 250 ms 釋放。比較入口時同時列出實際指令速率與放開時間。
7. 每條件只有 3 輪，只能看出大差異；0 掉包不能寫成「不會掉包」，要附分母。

## 10. 限制與未決事項

**限制**
- 跑步機端只有段末淨值：漏反應和多反應會互相抵銷。
- ④ 未量測時，無法區分入口輸出失敗與跑步機未接受。
- 面板讀數代表設定值，不是實際帶速。
- 單一機型、單一台 Arduino，結果不能推到其他設備。
- 目前的測試韌體不是原版韌體；A、B 的結果不能直接代表原版系統，那是 C 的工作。

**未決**
- ④ 的硬體：第二塊 Nano 加接收模組、邏輯分析儀是否可用。參考接收器本身也會漏收，使用前要先校正。
- 時程：研討會紀錄原訂 2026-11-27 完成實驗，能否延後。
- T2 的結果決定 A 的 gap 級距。
- B 的間隔水準與 C 的節奏在實作前確認。
