# 台架驗收與前測清單

這份清單有兩個用途：一是確認兩支測試韌體在實機上的行為和協定一致，二是在開始正式條件矩陣之前，先跑一輪前測，確認資料流程可以從頭走到尾。照順序做，每完成一項就打勾；沒通過的項目，在「紀錄」欄寫下實際看到的結果。

- 韌體：`Arduino/StressTest_Opto`、`Arduino/StressTest_RF`，兩支都是 v0.3.0
- 規格與協定：`Docs/StressTest-Spec.md`
- 安全守則：測試期間跑帶上不站人，原廠的停止鍵要隨時按得到。

## B. 用序列埠監控視窗手動驗證韌體（不接跑步機）

**設定**：baud 選 115200，行尾選「Newline」。開啟監控視窗時 Nano 會自動重開機。光耦版可以在腳位 3～6 接 LED，或用三用電表量電壓。

### B-1 光耦版（StressTest_Opto）

| ✓ | 送出 | 預期 | 紀錄 |
|---|---|---|---|
| ☐ | （開機） | `READY,OPTO,0.3.0,press_ms=120;action_ms=120` | |
| ☐ | `HELLO` | 同上一行 | |
| ☐ | `ONE,UP`／`ONE,DOWN`／`ONE,STOP`／`ONE,START` | 腳位 3／4／5／6 依序亮約 0.12 秒，每次回 `ACK,ONE,…` | |
| ☐ | `ONE,XYZ` | `ERR,BAD_COMMAND` | |
| ☐ | `FOO` | `ERR,UNKNOWN` | |
| ☐ | `RUN,UP,40,0` | `ERR,BAD_RUN`（每段上限 32 筆） | |
| ☐ | `RUN,UP,20,0` | `ACK,RUN,UP,20,0`，接著 20 行 `T,i,start,end`，最後 `DONE,20` | |
| ☐ | 檢查上一步的 `T` | 每筆 `end − start` 約 120000 µs；下一筆 `start` − 上一筆 `end` 只有幾十到幾百 µs（間隔 0 ms） | |
| ☐ | `RUN,UP,5,10` | 每筆之間的間隔約 10000 µs | |
| ☐ | 送 `RUN,DOWN,20,10` 後立刻送 `ABORT` | `ABORTED,n`，n 小於 20；回報 n 行 `T` | |
| ☐ | 中止後量腳位 3～6 | 全部 LOW（LED 熄滅，或電壓約 0 V） | |
| ☐ | 閒置時送 `ABORT` | `ABORTED,0` | |
| ☐ | 送 `RUN,UP,20,10` 後馬上送 `ONE,UP` | 腳位 4 不動作，腳位 3 照常跑完；`DONE,20` 之後才回 `ERR,BUSY` | |

### B-2 RF 版（StressTest_RF）

| ✓ | 送出 | 預期 | 紀錄 |
|---|---|---|---|
| ☐ | （開機） | `READY,RF,0.3.0,bits=24;repeat=2;release_ms=250;action_ms=340` | |
| ☐ | `ONE,UP` | 約 0.34 秒後回 `ACK,ONE,UP` | |
| ☐ | `RUN,UP,5,0` | 每筆 `end − start` 約 340000 µs（RF 發射約 90 ms，加上 250 ms 釋放）。這是 `action_ms` 的實測值，請寫在紀錄欄。 | |
| ☐ | `ABORT`、`ERR,BUSY`、`BAD_RUN` | 行為和光耦版相同 | |

## E. 前測：40 筆、間隔 10 ms

每個入口各跑一輪。全程用手機錄下面板畫面，畫面裡要同時拍到電腦螢幕，之後才能對照時間。

| ✓ | 步驟 | 紀錄 |
|---|---|---|
| ☐ | 在右側矩陣點「10 ms × 40 次」 | |
| ☐ | 啟動後倒數 5 秒，接著預熱加速 10 次（1.0 → 2.0）；輸入面板讀數 2.0，按 Enter 兩次 | |
| ☐ | 畫面上方顯示「加速 已送 0／預計 20　減速 已送 0／預計 20」 | |
| ☐ | 段 1（加速 20 筆）結束時，看面板並輸入讀數；確認畫面的掉包數合理 | |
| ☐ | 段 2（減速 20 筆）同上 | |
| ☐ | 總結畫面按「跑帶已停止，回到設定」，矩陣這一格的進度 +1 | |
| ☐ | 光耦與 RF 各完成一輪 | |

## F. 紀錄檔

`TestLogs/` 內每次執行會產生 `commands_*.csv`、`segments_*.csv`、`rounds_*.csv` 三個檔案。手動單段則另存為 `manual_segments_*.csv`。

| ✓ | 項目 | 紀錄 |
|---|---|---|
| ☐ | 用 Excel 直接開啟（雙擊即可），中文沒有亂碼。檔案是 UTF-8 BOM 編碼。 | |
| ☐ | `commands_*.csv` 每輪有 40 列，`gap_us` 約 10000 | |
| ☐ | `segments_*.csv` 每輪有 2 列，`drops` 和畫面上顯示的一致 | |
| ☐ | `rounds_*.csv` 每輪有 1 列，`status` 為 `completed`；`up_planned`、`down_planned` 各為 20，`up_sent`、`down_sent` 與 Arduino 回報一致 | |
| ☐ | 做出第五章的掉包表（做法見下方） | |

**用 Excel 整理掉包表**

1. 開啟所有 `rounds_*.csv`，把資料列複製到同一張工作表，標題列只保留一次。
2. 篩選 `status = completed`。作廢的輪次不納入分析，但原始資料保留在檔案裡。
3. 插入樞紐分析表：
   - 列：`entry`
   - 欄：`gap_ms`
   - 篩選：`total_count`
   - 值：`total_drops`、`total_sent` 的加總，以及 `round_id` 的計數（就是輪數）。
4. 掉包率 = 總掉包 ÷ 總送出。報告時保留每一輪的數字，不要只合併成一個總成功率。
5. 如果 `any_possibly_clamped` 或 `any_report_short` 為 1，要個別說明那一輪，必要時回頭看錄影。

## 已知限制（寫進論文用）

- 判斷跑步機有沒有收到指令，是以「段」為單位：同一段裡如果「漏一筆」和「多一筆」同時發生，兩者會互相抵銷，從面板讀數看不出來。要逐筆核對，只能看錄影。
- 研究用的序號只存在 Unity 和 Arduino 之間；跑步機本身不會回報收到哪一筆。
