# RF／光耦 控制入口間隔壓力測試

這個專案測試跑步機的兩種控制方式會不會漏掉指令：**光耦**（V1，代替手指按面板）和 **433 MHz RF**（V2，代替遙控器）。

> 研究背景：研究問題一，「在相同加減速指令與不同發送間隔下，兩個控制入口能否正確輸出」。外部遙控器監聽（研究問題二）不在本專案範圍內。這是機器對機器的測試，沒有受試者。

## 實驗在做什麼

電腦叫跑步機加速或減速很多次，再比對**送了幾次**和**跑步機動了幾格**。少掉的部分，要查出是在哪裡少的。

```
電腦  ──USB──▶  Arduino  ──▶  光耦／RF 模組  ──▶  跑步機
```

| 畫面上的名稱 | 意思 |
|---|---|
| 序列端少 | 電腦送了，Arduino 沒收到 |
| 跑步機端少 | Arduino 做了，面板沒有跟著動。負數代表面板動得比指令多 |

例如電腦送 30，Arduino 收到並做了 29，面板動 27 格：序列端少 1，跑步機端少 2。目前量不到光耦或 RF 模組有沒有真的送出訊號，所以「跑步機端少」分不出是模組還是跑步機的問題。

| 送法 | 怎麼送 | 狀態 |
|---|---|---|
| **A 等回覆** | 電腦送一個，等 Arduino 回「做完了」，停一下，再送下一個 | 完成，未實機測 |
| **B 固定間隔** | 電腦照固定時間一直送，不等回覆 | 未實作 |
| **C 原版重現** | Arduino 照原版系統的方式處理指令 | 未實作 |
| **RUN 對照** | 電腦只說一次「做 n 個」，Arduino 自己連續做 | 完成，未實機測 |

完整說明（怎麼判斷結果、先試哪些項目、哪些事還沒決定）在 [Docs/ExperimentDesign.md](Docs/ExperimentDesign.md)。

## 測試設計

| 項目 | 設定 |
|---|---|
| 控制入口 | 光耦、RF |
| 休息間隔（gap） | 0／1／5／10 ms。A：電腦收到完成回覆後開始計時，實際空檔會更長。RUN：上一筆動作完成後開始計時 |
| 送法 | **A 等回覆**：電腦逐筆送，收到完成回覆後等 gap 再送下一筆。**RUN 對照**：Arduino 自己連續送完整段。右側面板切換，進度分開記 |
| 每段筆數 n | 30／60／90 筆 |
| 一輪的組成 | 加速 n → 減速 n → 加速 n → 減速 n，也就是 2 組，共 4n 筆（120／240／360） |
| 速度範圍 | 跑步機開機與最低速度都是 1.0 km/h；預熱到 2.0 後，在 2.0 和 2.0 + n × 0.1 之間來回（n=30 到 5.0、n=60 到 8.0、n=90 到 11.0），每次按鍵 ±0.1 km/h |
| 加減速次數 | 加速、減速各 2n 次。畫面和每輪 CSV 都會記下預計與實際送出的次數 |
| 重複次數 | 每個條件 3 輪（可調） |
| 條件總數 | 每種送法 4 種間隔 × 3 種 n × 2 種入口 = 24 個條件，共 72 輪 |

**一輪的流程**
1. 送出「啟動」，倒數 5 秒，等跑帶穩定。
2. 預熱：每秒加速 1 次，共 11 次，把速度從開機的 1.0 km/h 帶到 2.0 km/h。這段不計分。1.0 到 2.0 是 10 格，但實機上啟動後只送 10 次會停在 1.9，所以多送 1 次。起點設在 2.0，是為了和最低速度 1.0 之間留 10 筆的餘裕：加速段漏掉的筆數在 10 筆以內時，接下來的減速段才不會撞到底。
3. 研究人員確認面板顯示 2.0。如果不是 2.0，可以選「重新預熱」（用單發補足差額，不計分），或「以實際速度為起點繼續」。
4. 依序跑 4 段：加速 n、減速 n、加速 n、減速 n。每段送完 n 筆後研究人員輸入面板速度，確認後進入下一段。
5. 送出「停止」，顯示本輪總結。

單筆動作沿用正式版本的設定：
- **光耦**：每次按壓 120 ms。
- **RF**：24 bit 代碼，重送 2 次，送出後再等 250 ms 讓接收端判定「放開」。一筆約 340 ms。

測試版韌體拿掉了正式版的 800／1000 ms 冷卻時間。指令間隔由測試條件決定；A 送法另外包含電腦和 Arduino 之間的傳輸時間。

## 需要的東西

**軟體**
- Unity **6000.6.10f1**。專案已設定 API Compatibility 為 .NET Framework、Input Handling 為 Both。
- Arduino IDE。RF 版另外需要 [rc-switch](https://github.com/sui77/rc-switch) 函式庫，開發時用的是 2.6.4 版。

**硬體**
- Arduino Nano V3.0（ATmega328P）。兩種入口各燒一塊，或同一塊輪流燒錄。
- 光耦電路，接到跑步機面板按鍵。
- 433 MHz RF 發射模組。
- 跑步機：XTERRA DT168，速度範圍 1.0～12.0 km/h（上限已確認）。

## 快速開始

1. 把專案 clone 下來，用 Unity Hub 加入專案，以 6000.6.10f1 開啟。
2. 把 `Arduino/StressTest_Opto` 或 `Arduino/StressTest_RF` 燒錄到 Nano（見下一節）。
3. 在 Unity 開啟 `Assets/Scenes/StressTest.unity`，按 **Play**。測試介面會自動出現，不需要手動掛任何元件。
4. 在左側選擇入口和 COM port，按「連線」。狀態燈變成綠色就可以開始。
5. 在右側面板最上方確認送法是「**A 等回覆**」（正式實驗）。
6. 接下來每一步要做什麼、看哪裡，照[操作流程](#操作流程)的步驟 0～12 一步一步做。

> 第一次正式測試前，建議先照 [Docs/BenchAcceptance.md](Docs/BenchAcceptance.md) 做一次台架驗收和前測。

## 硬體接線與燒錄

| 韌體 | 腳位 | 用途 |
|---|---|---|
| `StressTest_Opto` | D3 | 加速 |
| | D4 | 減速 |
| | D5 | 停止 |
| | D6 | 啟動 |
| `StressTest_RF` | D10 | RF 發射（TX） |

> 韌體 v0.5.0 加入 A 送法需要的 `ZERO`、`CMD`、`STAT`。**兩塊板子都要重新燒錄**；舊韌體連得上，但程式會拒絕開始 A 送法的輪次。

**燒錄設定**
- 開發板選「Arduino Nano」，處理器選「ATmega328P」。上傳失敗的話改選「ATmega328P (Old Bootloader)」。
- 序列埠 baud 是 **115200**。燒錄完成後，用序列埠監控視窗（行尾選「Newline」）應該會看到：
  - 光耦版：`READY,OPTO,0.5.0,press_ms=120;action_ms=120;max_run=90;ack=1`
  - RF 版：`READY,RF,0.5.0,bits=24;repeat=2;release_ms=250;action_ms=340;max_run=90;ack=1`
- **燒錄完記得關掉序列埠監控視窗**，否則 Unity 連線時會顯示「被其他程式占用」。

## 操作流程

以下照實際測試的順序，一步一步說明。每一步分三點：

- **做什麼**：你要動手做的事。
- **看哪裡**：畫面上要看的位置。
- **怎麼看**：畫面長什麼樣子才算正確，不對的話怎麼處理。

> 截圖是用模擬韌體拍的，畫面上的數字只是示範。**目前的截圖還是舊版設計（每段 20 筆、40／80／120 次、預熱 10 次、韌體 0.3.0）拍的**，版面位置相同，數字和矩陣欄位請以內文為準。全部 25 個畫面的完整說明在 [Docs/UI-Screens.md](Docs/UI-Screens.md)。

### 先認識畫面

![畫面的三個區域](Docs/screenshots/ui/05_idle.png)

畫面固定分成三塊，之後每一步都會用到這三個名稱：

| 位置 | 名稱 | 裡面有什麼 |
|---|---|---|
| 最上面一條 | **狀態列** | 左邊是**圓形燈號**和連線狀態；右邊是「中斷連線」和紅色的「**緊急停止（空白鍵）**」 |
| 左邊大塊 | **「現在要做的事」** | 現在該做的那一件事。**綠色的大按鈕就是下一步要按的**，每個畫面只有一顆 |
| 右邊大塊 | **條件矩陣** | 4 種間隔 × 3 種 n，每一格寫著光耦、RF 各完成幾輪 |

燈號的顏色：⚪ 灰色是還沒連線，🟡 黃色是正在連線，🟢 綠色是已連線、可以測試，🔴 紅色是出問題了，看燈號旁邊的文字。

> **安全**：n = 90 時跑帶會升到 11 km/h，跑帶上和後方都不要有人或東西。不管進行到哪一步，只要覺得不對勁，按鍵盤的**空白鍵**就是緊急停止。跑步機沒有反應的話，直接按跑步機本體的停止鍵。

### 步驟 0：開始前的準備（不用開程式）

**做什麼**
1. 把要測的入口韌體燒到 Nano：測光耦燒 `Arduino/StressTest_Opto`，測 RF 燒 `Arduino/StressTest_RF`。燒錄方法見[硬體接線與燒錄](#硬體接線與燒錄)。
2. **關掉 Arduino IDE 的序列埠監控視窗。** 沒關的話，程式會連不上。
3. 把 Nano 的 USB 線接到電腦，跑步機插電。
4. **跑帶上不要站人**，跑步機本體的停止鍵要放在你伸手按得到的地方。
5. 架好手機錄影，畫面要**同時拍到跑步機面板和電腦螢幕**。之後懷疑某一段的結果時，可以回頭看。

### 步驟 1：開啟測試程式

![尚未連線](Docs/screenshots/ui/01_disconnected.png)

**做什麼**：在 Unity 開啟 `Assets/Scenes/StressTest.unity`，按上方的 **Play** ▶；如果用的是建置好的執行檔，直接雙擊 `StressTest.exe`。

**看哪裡**：狀態列左上角的燈號，以及左邊「現在要做的事」。

**怎麼看**：燈號是**灰色**，旁邊寫「尚未連線」；左邊顯示「連線到 Arduino」。看到這個畫面就是正常的。

---

### 步驟 2：連線到 Arduino

**做什麼**
1. 左邊「**1. 選擇入口**」：測光耦按「光耦」，測 RF 按「RF」。**必須和板子上燒的韌體一致。**
2. 「**2. 選擇 COM port**」：按 Nano 所在的 COM port，例如 `COM3`。列表是空的，就按右邊的「重新整理」。
3. 按綠色的「**3. 連線**」。

**看哪裡**：狀態列的燈號和燈號旁邊的文字。

**怎麼看**
- 燈號先變**黃色**，顯示「等待韌體回報身分…」，大約 2 秒。這是 Nano 正在重開機，屬於正常現象。
- 接著變**綠色**，顯示「已連線：光耦韌體 v0.5.0」（或 RF），下方小字是韌體參數。**看到綠燈就成功了**，畫面會變成步驟 3 的樣子。

**連不上時：**

| 畫面 | 燈號／文字 | 原因 | 怎麼處理 |
|---|---|---|---|
| ![入口不符](Docs/screenshots/ui/02_entry_mismatch.png) | 🔴「入口不符：選了光耦，板子是 RF 韌體」 | 選的入口和板子上的韌體不一樣 | 按左邊的「中斷連線，重新選擇」，改選正確的入口，或換一塊板子 |
| ![連線逾時](Docs/screenshots/ui/04_handshake_timeout.png) | 🔴「逾時：4 秒內沒有收到韌體回報」 | 板子上不是測試韌體，或 baud 不對 | 重新燒錄測試韌體，再連一次 |
| （紅字顯示在左邊） | 「COM3 被其他程式占用」 | 序列埠監控視窗還開著 | 關掉 Arduino IDE 的序列埠監控視窗，再按連線 |

### 步驟 3：確認下一輪要測什麼，按「開始下一輪」

![已連線、閒置](Docs/screenshots/ui/05_idle.png)

**做什麼**：先在右側面板最上方選送法（**A 等回覆**是正式實驗，**RUN 對照**是對照組），看清楚左邊寫的條件，確認無誤後按綠色的「**開始下一輪**」。

**看哪裡**：左邊「現在要做的事」由上往下有四行：
1. 大字「**下一輪（A）：光耦、間隔 1 ms、n = 30**」：這一輪的送法、入口、間隔、每段筆數。
2. 「**（加速 30、減速 30）× 2 組＝共 120 筆，分 4 段**」：這一輪的組成。
3. 「第 1 輪……預熱加速 11 次到 2.0 後開始計分（2.0↔5.0）」：這是同一個條件的第幾輪，以及速度會在什麼範圍內來回。
4. 小字「依整體排程下一輪輪到 RF；也可以先繼續用光耦」：照整體排程該換板子時，才會出現這一行。

**怎麼看**
- 入口要和你接的板子一致。條件不用自己挑，系統會照排程選好。
- 想指定某個條件（例如補做），改按右邊矩陣裡的那一格。
- 矩陣每一格的「光耦 1/3、RF 1/3」，代表這個條件兩個入口各完成了 1 輪，目標是 3 輪。

### 步驟 5：預熱（不用操作）

![預熱](Docs/screenshots/ui/08_round_warming_up.png)

**做什麼**：什麼都不用做。系統每秒按一次加速，共 11 次。

**看哪裡**：左邊的大字「**預熱加速：4／11**」，以及跑步機面板。

**怎麼看**：數字每秒加 1。11 次裡面有 1 次面板不會動（所以多送這 1 次），其餘每次加 0.1，結束時應該停在 **2.0**。預熱不計分，只是先把速度帶到起點。如果哪次 11 下全部生效、停在 2.1，步驟 6 選「重新預熱」會補 1 次減速。

### 步驟 6：確認起點速度是 2.0

| ① 輸入面板讀數 | ② 確認 |
|---|---|
| ![輸入起點讀數](Docs/screenshots/ui/09_round_warmup_reading.png) | ![確認起點](Docs/screenshots/ui/10_round_warmup_confirm.png) |

**做什麼**
1. 抬頭看**跑步機面板**上的速度。
2. 把讀數打進左邊的輸入框，例如面板顯示 2.0，就打 `2.0`，也可以打 `20`。輸入框已經自動選好，直接打字就可以。
3. 按 **Enter**。
4. 畫面變成「你輸入的面板速度：2.0 km/h」，確認沒打錯，再按一次 **Enter**。

**看哪裡**：左邊大字「**請看面板，預期 2.0 km/h**」，這是系統預期面板應該顯示的數字。

**怎麼看**
- 面板就是 2.0：照打，按兩次 Enter，開始第一段。
- 打錯了：在第二個畫面按 **Esc**，回去重打。
- **面板不是 2.0**（例如 1.8）：按 Enter 之後會出現下面這個畫面，二選一：

  ![預熱讀數不符](Docs/screenshots/ui/16_round_warmup_mismatch.png)

  - 「**重新預熱（補足差額）**」：建議選這個。系統會補按差的次數，例如 1.8 → 2.0 補 2 次加速、2.1 → 2.0 補 1 次減速，然後回到 ① 重新確認。
  - 「**以 1.8 為起點繼續**」：不補，直接用 1.8 當起點開始計分。

### 步驟 7：段執行中（不要操作）

![段執行中](Docs/screenshots/ui/11_round_running_segment.png)

**做什麼**：**什麼都不要按。** 這一段的 n 筆指令正在送出。n = 90 時，光耦一段約 11 秒以上，RF 約 31 秒以上。A 送法執行期間程式會占滿一個 CPU 核心，這是正常的；請不要同時跑其他吃資源的程式。

**看哪裡**：左邊上方「本輪（A）：間隔 1 ms、n = 30（共 120 筆）　**段 1／4**」；大字「**執行中：加速 30 筆**」；以及藍色進度條。A 送法另外顯示「已送 k、已回覆 r」。

**怎麼看**
- A 送法的進度條是實際回覆數；RUN 對照的進度條是**預估**時間，跑滿之前畫面就可能先換掉。
- A 送法中「已回覆」停住超過幾秒，代表有指令沒有回覆，程式會在逾時後繼續；連續 3 筆沒回覆就結束這一段。
- 這時跑步機面板的速度會一路往上加（或往下減）。
- 有異狀就按**空白鍵**緊急停止。

---

### 步驟 8：看面板，輸入這一段結束時的速度

![輸入段終點讀數](Docs/screenshots/ui/12_round_segment_reading.png)

**做什麼**
1. **等面板的數字停下來不再變**，再讀數字。
2. 把面板顯示的速度打進輸入框，例如面板顯示 4.7，就打 `4.7` 或 `47`。**10 以上要打 `11.0` 或 `110`**；只打 `11` 會被當成 1.1。
3. 按 **Enter**。

**看哪裡**：左邊大字「**請看面板，預期 5.0 km/h**」，以及跑步機面板。

**怎麼看**
- 預期 5.0、面板也是 5.0：這一段沒有看到掉包。
- 預期 5.0、面板是 4.7：差 0.3 km/h，代表漏了 3 筆。這正是要測的掉包，**照實輸入就好**，不用改成預期值。
- 輸入框上方出現黃色或粗體的提醒，例如「Arduino 只回報 27 筆」或「預期低於最低速度 1.0」，請先看步驟 9 的旗標說明，然後一樣**照面板的實際讀數輸入**。

---

### 步驟 9：確認系統推算的掉包數

![確認掉包](Docs/screenshots/ui/13_round_segment_confirm.png)

**做什麼**：檢查畫面上的數字，沒問題就按 **Enter** 進入下一段；打錯就按 **Esc** 回步驟 8 重打。

**看哪裡**
- 大字「**面板 4.7 km/h → 推算掉包 3 筆**」：這一段的結果。
- 下一行「預期變化 +3.0 km/h，實際 +2.7 km/h；Arduino 回報 30 筆」：
  - **預期變化**：照指令應該變多少（30 筆 × 0.1 = 3.0）。
  - **實際變化**：面板實際變了多少。
  - **Arduino 回報**：Arduino 說它真的送出了幾筆。

- A 送法多一行各檢查點的筆數：「電腦送 30 → Arduino 收 30 → 執行 30 → 面板 27 格（序列端少 0、跑步機端少 3）」。這行指出掉在哪一段。

**怎麼看**
- **Arduino 回報 30 筆，但掉包 3 筆**：Arduino 確實送出了 30 筆，跑步機只反應了 27 筆，這就是**跑步機那一端的掉包**，正是這個實驗要量的東西。
- 出現粗體的旗標（見下圖）時，照下表處理。旗標不一定代表資料不能用：

  ![旗標](Docs/screenshots/ui/18_round_clamped_confirm.png)

  | 旗標 | 意思 | 建議 |
  |---|---|---|
  | 「**可能觸底／觸頂**」 | 理論終點超出 1.0～12.0，多出來的指令被跑步機吃掉了 | 這段的跑步機端數字不可信，結束後作廢這一輪 |
  | 「**Arduino 回報不足**」（RUN） | Arduino 回報的筆數比應送的少，問題可能在電腦或序列埠，不一定是跑步機 | 對照錄影，考慮作廢 |
  | 「**有指令沒有完成往返**」（A） | 有指令遺失、毀損或沒回覆 | **這是要收集的資料，不要因此作廢** |
  | 「**Arduino 在這段中重新開機**」 | 執行中板子重開 | 檢查供電，記下發生情況 |

### 步驟 10：重複步驟 7～9，直到所有段跑完

**做什麼**：照步驟 7 → 8 → 9 的順序，把剩下的段做完。

**看哪裡**：左邊上方的「**段 2／4**」，以及「**加速 已送 30／預計 60　減速 已送 0／預計 60**」。

**怎麼看**
- 固定 4 段，加速和減速輪流。以 n = 30 為例：2.0 → 5.0 → 2.0 → 5.0 → 2.0。
- n 越大，頂端速度越高：n = 60 到 8.0，n = 90 到 11.0。
- 「已送」是 Arduino 回報實際送出的次數，跑完時應該和「預計」一樣。
- 每一段都從上一段**你輸入的實際讀數**開始算，所以前一段漏掉的部分不會重複算進下一段。

### 步驟 11：看本輪總結，離開這一輪

![本輪總結](Docs/screenshots/ui/14_round_summary.png)

**做什麼**
1. 確認跑步機的**跑帶已經完全停下來**。最後一段結束後，系統會自動送出停止指令。
2. 結果沒問題：按綠色的「**跑帶已停止，回到設定**」。
3. 結果有問題，例如看錯面板、中途有人碰到跑步機、板子重開機、出現「可能觸底／觸頂」：在「作廢原因」欄寫下原因，按「**作廢此輪**」。A 送法的「有指令沒有完成往返」是要收集的資料，不要因此作廢。

   ![作廢此輪](Docs/screenshots/ui/15_round_void_reason.png)

**看哪裡**
- 大字「**本輪完成：總掉包 3／120 筆**」：這一輪的總結果。
- 下面每一行是一段，例如「段 1：加速 30 筆，2.0 → 4.7，掉包 3」。
- 「加速：預計 60、Arduino 實送 60　減速：預計 60、Arduino 實送 60」：兩個數字應該一致。
- 「紀錄位置」：CSV 存在哪個資料夾。

**怎麼看**
- **一定要按其中一顆按鈕**，這一輪才會寫進每輪紀錄、計入右邊矩陣的進度。
- 作廢的輪次，原始資料還是會保留，只是不計入進度，之後需要重做那個條件。

### 步驟 12：跑下一輪，或換板子

**做什麼**：回到步驟 3 的畫面後，按「開始下一輪」繼續測。

**看哪裡**：左邊有沒有出現小字「**依整體排程下一輪輪到 RF（或光耦）**」，以及右邊矩陣的進度。

**怎麼看**
- 沒有這行小字：照常按「開始下一輪」。
- 出現這行小字：代表照排程該換另一個入口了。你可以先繼續用目前的板子，等這個入口的條件都做完再換。要換的話：按狀態列的「中斷連線」→ 換板子或重新燒錄 → 回到步驟 2。
- 左邊顯示「**光耦已完成所有條件**」：這個入口全部做完了，換另一個入口。
- 可以分好幾天測。下次打開程式時，右邊矩陣會自動從紀錄檔還原進度（「已從 N 個紀錄檔還原 M 輪完成紀錄」）。舊版設計（沒有 `n`、`sets` 欄）的紀錄檔不計入進度。

### 手動工具（硬體檢查用）

![手動工具](Docs/screenshots/ui/06_idle_manual_tools.png)

**做什麼**：在步驟 3 的畫面按「**展開手動工具（單發、手動單段）**」。

**用途**
- **單發測試**：按「啟動」「加速」「減速」「停止」，各送一次指令，用來確認接線和跑步機有沒有反應。例如按「加速」，面板應該 +0.1。

## 紀錄檔（CSV）

所有紀錄都寫在專案根目錄的 `TestLogs/` 底下。右側面板有「開啟紀錄資料夾」按鈕可以直接打開。

紀錄檔的格式：
- 編碼是 UTF-8 BOM，用 Excel 直接開啟，中文不會變亂碼。
- 每寫入一列就立刻存檔，所以即使 Unity 當掉，已經確認過的段也不會遺失。
- 程式每次執行，在第一次開始輪次時產生一組新檔，檔名帶有時間戳記。手動單段的檔案在第一次輸入手動讀數時產生。

| 檔案 | 一列代表 | 什麼時候寫入 |
|---|---|---|
| [`commands_*.csv`](#commands逐筆指令) | 一筆指令 | 按下 Enter 確認某一段的讀數時，一次寫入該段全部 |
| [`segments_*.csv`](#segments每一段) | 一段（加速 n 或減速 n） | 同上 |
| [`rounds_*.csv`](#rounds每一輪) | 一輪 | 在總結畫面或中斷畫面按按鈕離開時 |
| [`manual_segments_*.csv`](#manual_segments手動單段) | 手動工具跑的一段 | 輸入手動段的讀數時 |
| `manual_commands_*.csv` | 手動段的一筆指令 | 同上 |

哪些情況**不會**留下紀錄：
- 被緊急停止打斷、或還沒確認讀數的段，不寫入 `commands_*.csv` 和 `segments_*.csv`。
- 一輪跑到一半就中斷連線或關閉程式，`rounds_*.csv` 沒有這一輪的列；已確認的段仍在另外兩個檔案裡。整理資料時，只分析 `rounds_*.csv` 裡有 `status = completed` 的 `round_id`。

### 共通的寫法

| 項目 | 寫法 |
|---|---|
| 速度 | 單位 km/h，固定一位小數 |
| 時間長度 | 欄名以 `_us` 結尾的是微秒（µs），1 ms = 1000 µs |
| 旗標 | `1` 代表成立，`0` 代表不成立 |
| `entry` | `OPTO`（光耦）或 `RF` |
| `direction` | `UP`（加速）或 `DOWN`（減速） |
| `segment_index` | 輪內第幾段，**從 0 起算**：0＝第 1 組加速、1＝第 1 組減速、2＝第 2 組加速、3＝第 2 組減速 |
| `round_id` | `日期-時間-入口-送法-G間隔-Nn`，例如 `20261127-143000-OPTO-A-G5-N60`。三份檔案用它互相對應 |
| `send_mode` | `A`（等回覆）或 `RUN`（對照） |
| `recorded_at` | 寫入這一列時的電腦時間（`yyyy-MM-dd HH:mm:ss`） |
| 空白 | 代表沒有這個值（各欄說明會寫什麼情況下空白） |

### commands：逐筆指令

用途：看每一筆指令走到哪裡，以及實際間隔。A 送法**每送出一筆就有一列**（沒有回覆的也有）；RUN 對照只有 Arduino 回報時間戳的筆。這份檔案**看不出跑步機有沒有收到**某一筆。

| 欄位 | 意思 |
|---|---|
| `round_id` | 所屬輪次 |
| `entry` | 控制入口 |
| `gap_ms` | 設定的休息間隔（ms） |
| `n` | 本輪每段的筆數 |
| `sets` | 本輪的組數（正式實驗為 2） |
| `segment_index` | 第幾段（從 0 起算） |
| `seq` | 段內第幾筆，從 0 起算 |
| `direction` | 這一筆是加速還是減速 |
| `start_us` | 這一筆動作開始時 Arduino 的 `micros()` |
| `end_us` | 這一筆動作結束時的 `micros()`。光耦是腳位拉回 LOW 之後；RF 是發射完再等完 250 ms 釋放時間之後 |
| `gap_us` | 實際休息時間＝本筆 `start_us` − 上一筆 `end_us`。每段第一筆，以及前一筆沒有時間戳時空白 |
| `send_mode` | 送法 |
| `cmd_seq` | A：協定上的指令序號，連線期間一直遞增。RUN 空白 |
| `status` | A：`done`（期限內回覆）、`late`（逾時後才回覆）、`rejected`（Arduino 回報行毀損）、`no_reply`（沒有回覆）、`pending`（段在回覆前就結束，例如重新開機）。RUN 空白 |
| `pc_send_us` | A：電腦送出的時間（電腦時鐘，µs，程式啟動起算） |
| `pc_reply_us` | A：電腦收到完成回覆的時間；沒有回覆時空白。`pc_reply_us − pc_send_us` 是往返時間 |
| `rx_us` | A：Arduino 讀完這行指令時的 `micros()` |

- `end_us − start_us` 是單筆動作耗時：光耦約 120000，RF 約 340000（推算值，以實測為準）。
- `micros()` 從 Arduino 開機起算，約 71.6 分鐘歸零一次。`gap_us` 已經處理歸零；自己用 `start_us`、`end_us` 相減時，遇到負值要加上 4294967296。
- RUN 對照中，段逾時的段沒有任何逐筆列；Arduino 回報不足的段只有實際回報的那幾筆。
- A 送法沒有回覆的列，`start_us`、`end_us`、`rx_us` 空白。
- 電腦時鐘和 Arduino 的 `micros()` 沒有同步，兩者不能直接相減。

### segments：每一段

用途：掉包的主要資料。每一列是「面板讀數推算出的一段結果」。

| 欄位 | 意思 | 來源 |
|---|---|---|
| `recorded_at` | 確認這段讀數的時間 | 電腦 |
| `round_id` | 所屬輪次 | 系統 |
| `segment_index` | 第幾段（從 0 起算） | 系統 |
| `entry` | 控制入口 | 韌體回報 |
| `firmware_version` | 韌體版本 | 韌體回報 |
| `direction` | 加速段或減速段 | 系統 |
| `count` | 這段**應送**的筆數（＝n） | 系統 |
| `gap_ms` | 設定的休息間隔（ms） | 系統 |
| `start_speed` | 這段開始時的面板速度。第 1 段是預熱後確認的讀數，之後各段是上一段的 `actual_end` | 研究人員輸入 |
| `expected_end` | 指令全部生效時應該到達的速度＝`start_speed` + `expected_change`。這是理論值，可能超出跑步機範圍（例如低於 1.0） | 計算 |
| `actual_end` | 這段結束時面板實際顯示的速度 | 研究人員輸入 |
| `expected_change` | 預期變化量，加速為正、減速為負：±`count` × 0.1 | 計算 |
| `actual_change` | 實際變化量＝`actual_end` − `start_speed` | 計算 |
| `drops` | 推算掉包數＝\|`expected_change` − `actual_change`\| ÷ 0.1，四捨五入。判讀限制見[掉包怎麼算](#掉包怎麼算) | 計算 |
| `reported_count` | Arduino 回報實際執行的筆數。RUN：`DONE` 的筆數，段逾時時空白。A：`STAT` 的執行數，問不到時用完成回覆數 | 韌體回報 |
| `report_short` | `1`＝逾時、重新開機，或回報筆數、時間戳筆數少於 `count`。A 送法中代表有指令沒有完成往返，是結果不是排除條件 | 判定 |
| `timed_out` | RUN：`1`＝期限內沒收到 `DONE`。A：`1`＝連續 3 筆沒有回覆而提早結束 | 判定 |
| `possibly_clamped` | `1`＝`expected_end` 低於 1.0 或高於 12.0，這段的 `drops` 不可信 | 判定 |
| `mean_gap_us` | 這段實際休息時間的平均（一位小數）；時間戳少於 2 筆時為 `0.0` | 時間戳 |
| `max_gap_us` | 這段實際休息時間的最大值；時間戳少於 2 筆時為 `0` | 時間戳 |
| `send_mode` | 送法 | 系統 |
| `pc_sent` | A：電腦實際送出的指令數 | 電腦 |
| `arduino_received` | A：Arduino 通過檢查碼的指令數；`STAT` 問不到時空白 | 韌體回報 |
| `arduino_executed` | A：Arduino 做完動作的指令數 | 韌體回報 |
| `arduino_bad` | A：Arduino 收到的毀損、過長或不認得的行數 | 韌體回報 |
| `replies` | A：電腦收到的完成回覆數（含遲到） | 電腦 |
| `rejected` | A：狀態為 `rejected` 的筆數 | 電腦 |
| `no_reply` | A：狀態為 `no_reply` 的筆數 | 電腦 |
| `panel_steps` | 面板往指令方向移動的格數（0.1 km/h 一格），往反方向為負 | 計算 |
| `link_lost` | A：`pc_sent` − `arduino_received`（電腦到 Arduino 掉的筆數） | 計算 |
| `treadmill_missing` | 執行數 − `panel_steps`（Arduino 之後掉的筆數，負值是多反應）。A 用 `arduino_executed`，RUN 用 `reported_count` | 計算 |
| `rebooted` | `1`＝這段執行中 Arduino 重新開機 | 判定 |

RUN 對照的 `pc_sent`、`arduino_*`、`replies`、`rejected`、`no_reply`、`link_lost` 空白。

### rounds：每一輪

用途：確認每一輪能不能用，以及做總表。矩陣進度也是從這份檔案還原的。

| 欄位 | 意思 |
|---|---|
| `recorded_at` | 離開總結畫面、寫入這一列的時間 |
| `round_id` | 輪次 ID |
| `entry` | 控制入口 |
| `firmware_version` | 韌體版本 |
| `firmware_params` | 韌體回報的參數，以分號分隔，例如 `press_ms=120;action_ms=120;max_run=90` |
| `gap_ms` | 設定的休息間隔（ms） |
| `n` | 每段筆數（30／60／90） |
| `sets` | 組數（2） |
| `total_count` | 整輪計畫送出的總筆數＝2 × `sets` × `n` |
| `segments` | 實際完成並確認的段數。小於 2 × `sets` 代表這一輪沒跑完 |
| `total_sent` | 已確認各段的**應送**筆數加總。名稱雖是 sent，實際送出的次數要看 `up_sent` + `down_sent` |
| `total_drops` | 已確認各段 `drops` 的加總，**包含**有旗標的段 |
| `warmup_reading` | 計分開始前最後一次確認的面板速度（正常是 2.0）；還沒到這一步就中斷時空白 |
| `end_reading` | 最後一個已確認段的 `actual_end`；沒有任何段時空白 |
| `any_possibly_clamped` | `1`＝至少一段 `possibly_clamped` |
| `any_report_short` | `1`＝至少一段 `report_short` |
| `mean_gap_us` | 整輪所有實際休息時間的平均（不含段與段之間讀面板的時間） |
| `max_gap_us` | 整輪實際休息時間的最大值 |
| `up_planned` | 計畫的加速次數＝`sets` × `n` |
| `down_planned` | 計畫的減速次數＝`sets` × `n` |
| `up_sent` | 已確認加速段中，Arduino 回報實際送出的次數（逾時段算 0） |
| `down_sent` | 已確認減速段中，Arduino 回報實際送出的次數（逾時段算 0） |
| `warmup_up` | 預熱與重新預熱中，Arduino 已回覆的單發加速次數。正常是 11（含跑步機沒有反應的 1 次），不計分 |
| `warmup_down` | 重新預熱中的單發減速次數，正常是 0，不計分 |
| `send_mode` | 送法 |
| `pc_sent` | A：各段 `pc_sent` 合計 |
| `arduino_received` | A：各段合計；任一段不明時空白 |
| `arduino_executed` | A：各段合計；任一段不明時空白 |
| `link_lost` | A：各段合計；任一段不明時空白 |
| `treadmill_missing` | 各段合計（含有旗標的段）；任一段不明時空白 |
| `any_rebooted` | `1`＝至少一段重新開機 |
| `status` | `completed`（可分析）或 `voided`（作廢：手動作廢、緊急停止、中途失敗） |
| `void_reason` | 作廢原因；`completed` 時空白。原因裡的半形逗號會改成全形 |

### manual_segments：手動單段

欄位與 `segments_*.csv` 完全相同，但 `round_id` 和 `segment_index` 空白，`start_speed` 是手動填入的「目前面板速度」。這些資料不計入矩陣進度。

`manual_commands_*.csv` 的欄位與 `commands_*.csv` 相同，`round_id`、`sets`、`segment_index` 空白，`n` 是這一段填的筆數。

### 整理論文用的掉包表

建議用 `segments_*.csv`，因為它能分開加速和減速，也能排除不可信的段。分析原則見[實驗設計第 8 節](Docs/ExperimentDesign.md#8-整理數據的規則)。

1. 把所有 `rounds_*.csv` 合併，篩出 `status = completed` 的 `round_id`。
2. 把所有 `segments_*.csv` 合併，只留下 `round_id` 在上一步清單裡的列。
3. 跑步機端指標（`drops`、`treadmill_missing`）排除 `possibly_clamped = 1` 的列；RUN 對照另外排除 `report_short = 1`。A 的鏈路端指標（`link_lost`、`rejected`、`no_reply`）不排除。記下排除了幾段。
4. 建立樞紐分析表：列放 `send_mode`、`entry`、`gap_ms`，欄放 `direction`，值放 `link_lost`、`treadmill_missing`、`drops` 和 `count` 的加總。要看 n 的影響時，把 `count` 放到篩選或欄位。
5. 各指標分別除以分母並保留各輪的數字：`link_lost` ÷ `pc_sent`；`treadmill_missing` ÷ `arduino_executed`（RUN 用 `reported_count`）。`drops` 以計畫的 n 計算，只有 `pc_sent`＝`count` 的 A 段才能使用。

詳細步驟見 [BenchAcceptance.md 的 F 節](Docs/BenchAcceptance.md#f-紀錄檔)。

## 掉包怎麼算

A 送法看兩個數字：**序列端少**（`link_lost`）和**跑步機端少**（`treadmill_missing`），意思見[實驗在做什麼](#實驗在做什麼)。另外有一個由面板直接推算的數字：

```
推算掉包數 = | 預期變化 − 面板實際變化 | ÷ 0.1   （四捨五入）
```

- **預期變化**：方向 × 筆數 × 0.1 km/h。
- **實際變化**：這段結束時的讀數減去這段開始時的讀數。每段的起點用上一段結束時的**實際讀數**，不用理論值，這樣誤差才不會一段段累積下去。

公式取絕對值，所以面板變化**比預期多**（例如一筆指令被跑步機算成兩次，或按住被當成長按連續加速）也會算進 `drops`。要分辨兩者，比較 `|actual_change|` 和 `|expected_change|`：小於是漏反應，大於是多反應。

休息間隔 `gap_ms` 在 RUN 對照是從上一筆**動作結束**起算；A 送法是從**電腦收到完成回覆**起算，實際空檔還要加上序列往返時間，以 `gap_us` 為準。RF 的單筆動作本身包含 250 ms 釋放時間，所以 RF 兩次發射之間的空檔是 250 ms 再加上述空檔；光耦兩次按壓之間腳位為 LOW 的時間就是上述空檔。論文比較兩個入口時需要交代這個差別。

段結果的旗標：

| 旗標 | 意思 |
|---|---|
| `possibly_clamped`（可能觸底／觸頂） | 起點加上預期變化後超出 1.0～12.0 km/h（跑步機最低 1.0），多出來的指令會被跑步機吃掉，這段推算出來的掉包數不可信。 |
| `report_short`（回報不足） | 回報的筆數少於應送筆數、逾時或重開機。RUN：問題可能出在序列埠或韌體。A：有指令沒有完成往返，是掉包資料。 |
| `timed_out` | RUN：在「筆數 ×（單筆動作時間 + 間隔）× 2 + 2 秒」內沒有收到 `DONE`。A：連續 3 筆沒有準時回覆。 |

Arduino 用 `micros()` 記錄每一筆的開始和結束時間。RUN 對照先把時間戳存在 RAM，整段跑完才一次回傳，執行期間不輸出任何序列資料，避免傳輸時間把間隔拉長；A 送法每做完一筆就回覆一行。

測試只透過一個接縫進行：`ISerialLink`，也就是「送一行、收一行」。測試用 C# 寫的 `FakeArduino` 模擬韌體，驅動整個流程，不需要接任何硬體。

- **在 Unity 中執行**：Window → General → Test Runner → EditMode → Run All。
- **用命令列執行**：先關閉開著這個專案的 Unity 編輯器，再執行：

```powershell
& "<Unity 安裝路徑>\6000.6.10f1\Editor\Unity.exe" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults results.xml -logFile unity.log
```

目前共有 153 個 EditMode 測試。其中 151 個核心流程測試在 Unity 之外用 .NET 8 跑過、全部通過；2 個專案設定測試需要在 Unity 內執行。

```powershell
& "<Unity 安裝路徑>\6000.6.10f1\Editor\Unity.exe" -batchmode -quit -projectPath . -executeMethod StressTest.EditorTools.StressTestBuild.BuildWindows -stresstest-build-path Build\StressTest.exe
```

**版面導覽**：執行檔加上參數 `-stresstest-tour <資料夾>` 啟動時，會接上內建的模擬韌體 `SimulatedArduino`，自動走過所有畫面，逐一截圖（共 25 張）後結束。[Docs/UI-Screens.md](Docs/UI-Screens.md) 裡的截圖就是這樣產生的：

## 序列協定

115200 baud，每行以 `\n` 結尾。兩支韌體使用同一套協定。

| Unity → Arduino | 意義 |
|---|---|
| `HELLO` | 要求韌體回報身分 |
| `ONE,<START\|UP\|DOWN\|STOP>` | 單發一次 |
| `RUN,<UP\|DOWN>,<n>,<gap_ms>` | 連續送 n 筆（n ≤ 90）；每筆動作完成後休息 gap_ms 毫秒 |
| `ABORT` | 中止執行中的 RUN |
| `ZERO` | 逐筆計數歸零（A 送法每段開始時） |
| `CMD,<seq>,<UP\|DOWN>*XX` | 逐筆指令：做一筆，做完回 `X` |
| `STAT` | 查詢逐筆計數 |

| Arduino → Unity | 意義 |
|---|---|
| `READY,<OPTO\|RF>,<版本>,<參數>` | 開機時或回應 HELLO；參數的 `max_run` 是單次 RUN 的筆數上限 |
| `ACK,<原指令>` | 已接受指令 |
| `T,<i>,<start_us>,<end_us>` | 第 i 筆的開始與結束時間；整段跑完後才一次送出 |
| `DONE,<n>` | RUN 完成 |
| `ABORTED,<n>` | RUN 被中止，n 為中止前已完成的筆數 |
| `ERR,<原因>` | 例如 `BAD_COMMAND`、`BAD_RUN`、`BUSY`（RUN 執行期間收到其他指令）、`UNKNOWN` |
| `X,<seq>,<rx_us>,<start_us>,<end_us>*XX` | 逐筆指令的完成回覆 |
| `NAK,BAD_LINE*XX` | `CMD` 行毀損，沒有執行 |
| `STAT,<收到>,<執行>,<毀損>*XX` | 回應 `STAT` |

`*XX` 是 `*` 之前所有位元組 XOR 的兩位大寫十六進位，例如 `CMD,1,UP*7E`。

### A 送法的收送規則

每一段的順序：

```
ZERO → ACK,ZERO → （CMD → X → 等 gap）重複 n 次 → STAT → STAT,收到,執行,毀損
```

| 情況 | 程式怎麼做 |
|---|---|
| 序號 | 連線期間一直增加，不重複，遲到的回覆不會配錯 |
| 指令沒有回覆 | 超過「2 × 單筆動作時間 + 1 秒」記為 `no_reply`，送下一筆。**不重送** |
| 連續 3 筆沒有準時回覆 | 結束這一段。遲到的回覆不會讓計數歸零 |
| 逾時後回覆才到 | 這一段還沒結束時記為 `late` |
| Arduino 回 `NAK` 或 `ERR` | 正在等回覆的那一筆記為 `rejected`，至少等 50 ms 再送下一筆 |
| `ZERO`、`STAT` 沒有回覆 | 最多問 3 次（不影響跑步機）。仍問不到時，Arduino 計數留空 |
| 段執行中或等讀數時 Arduino 重開機 | 標記 `rebooted`；段執行中會結束這一段 |
| `STAT` 的數字比收到的完成回覆少 | 代表計數中途歸零，Arduino 計數留空 |

電腦端用獨立執行緒收送，間隔不受畫面更新率限制。

## 已知限制

- **A 送法的實際空檔比 gap 長**：多出傳輸時間（尚未實測），可能蓋掉 0／1／5／10 ms 的差別。先做前測 T2。
- **光耦可能被當成長按**（推測，未實測）：兩次按壓之間放開時間很短時，面板可能看不到放開。做前測 T6。
- **RUN 對照的 RF 間隔差異很小**：每筆固定有 250 ms 釋放時間，gap 0 到 10 ms 的差別相對很小。
- **量不到模組輸出**：跑步機端少掉的指令，分不出是光耦／RF 模組還是跑步機造成。
- **部分重開機偵測不到**：Arduino 在回覆任何指令之前重開，而且開機訊息遺失時，程式不會發現。
- **以段為單位判定**：跑步機本身不會回報收到哪一筆指令，只能從每段的面板讀數推算。如果同一段裡同時「漏一筆」又「多一筆」，兩者會互相抵銷，看不出來。要逐筆核對只能看錄影。
- **RF 的 `action_ms=340` 是推算值**：由 frame 長度和釋放時間算出，只用於估計逾時和顯示進度條。實際耗時請看 CSV 裡的時間戳，並在台架驗收時填入實測值。
- **面板輸入的規則**：沒有小數點、且數值 ≥ 10 的整數會自動除以 10（例如 `27` → 2.7、`110` → 11.0）。n = 90 會到 11.0，只打 `11` 會變成 1.1，確認畫面要看清楚。
- **掉包超過 10 筆時下一段可能無法判讀**：某個加速段漏超過 10 筆，接下來的減速 n 筆理論終點就低於 1.0，會標記 `possibly_clamped`。n = 90 的第 2 組加速段，若前一個減速段比第 1 個加速段多漏超過 10 筆，也會超過 12.0。前測時先確認各間隔的掉包量，再決定起點速度是否需要調整。
- **預熱多送 1 次是依實機現象做的補償**：原因尚未確認（推測是啟動後第一下按鍵沒有作用）。如果跑步機在段與段之間閒置後也會吃掉第一下，每段會固定多 1 筆掉包；台架驗收時請照 D 節檢查。
