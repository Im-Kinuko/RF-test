# RF／光耦 控制入口間隔壓力測試

這個專案測試跑步機的兩種控制方式會不會漏掉指令：**光耦**（V1，代替手指按面板）和 **433 MHz RF**（V2，代替遙控器）。

> 研究背景：研究問題一，「在相同加減速指令與不同發送間隔下，兩個控制入口能否正確輸出」。外部遙控器監聽（研究問題二）不在本專案範圍內。這是機器對機器的測試，沒有受試者。

## 實驗在做什麼

電腦叫跑步機加速或減速很多次，再比對**送了幾次**和**跑步機動了幾格**。少掉的部分，要查出是在哪裡少的。

```
電腦  ──USB──▶  Arduino  ──▶  光耦／RF 模組  ──▶  跑步機
```

| 畫面上的名稱 | 意思 |
|---|---|
| 序列端少 | 電腦送了，Arduino 沒收到 |
| 跑步機端少 | Arduino 做了，面板沒有跟著動。負數代表面板動得比指令多 |

例如電腦送 20，Arduino 收到並做了 19，面板動 17 格：序列端少 1，跑步機端少 2。目前量不到光耦或 RF 模組有沒有真的送出訊號，所以「跑步機端少」分不出是模組還是跑步機的問題。

| 送法 | 怎麼送 | 狀態 |
|---|---|---|
| **A 等回覆** | 電腦送一個，等 Arduino 回「做完了」，停一下，再送下一個。整輪不停 | 完成，未實機測 |
| **B 固定間隔** | 電腦照固定時間一直送，不等回覆 | 未實作 |
| **C 原版重現** | Arduino 照原版系統的方式處理指令 | 未實作 |
| **RUN 對照** | 電腦只說一次「做這一段」，Arduino 自己連續做。每段停下來讀面板 | 完成，未實機測 |

完整說明（怎麼判斷結果、先試哪些項目、哪些事還沒決定）在 [Docs/ExperimentDesign.md](Docs/ExperimentDesign.md)。

## 測試設計

| 項目 | 設定 |
|---|---|
| 控制入口 | 光耦、RF |
| 休息間隔（gap） | 0／1／5／10 ms。A：電腦收到完成回覆後開始計時，實際空檔會更長。RUN：上一筆動作完成後開始計時 |
| 送法 | **A 等回覆**：電腦逐筆送，整輪中間不停。**RUN 對照**：Arduino 一次送一段，每段停下來讀面板。右側面板切換，進度分開記 |
| 每輪總次數 | 40／80／120 筆 |
| 每段筆數 | 20 筆（可調；A 上限 35、RUN 上限 40），加速段和減速段輪流 |
| 段數 | 40 次 2 段、80 次 4 段、120 次 6 段 |
| 速度範圍 | 跑步機開機與最低 1.0 km/h，**最高 6.0 km/h**。A 在 **2.5 ↔ 4.5** 之間來回；RUN 在 2.0 ↔ 4.0。每次按鍵 ±0.1 km/h |
| 預熱 | 每秒加速 1 次到起點：A 按 15 次，RUN 按 10 次。不計分 |
| 重複次數 | 每個條件 3 輪（可調） |
| 條件總數 | 每種送法 4 種間隔 × 3 種總次數 × 2 種入口 = 24 個條件，共 72 輪 |

**A 送法一輪的流程**

```
啟動、等 5 秒 → 預熱到 2.5 → 確認起點 →【開始錄影】
→ 整輪連續送出（加 20、減 20 輪流，中間不停）
→ 輸入最後速度 → 程式停止跑步機
→ 看影片輸入各轉向點 → 核對 → 完成
```

轉向點是換方向那一刻的面板速度（加速段結束是最高點，減速段結束是最低點）。40 次要讀 1 個、80 次 3 個、120 次 5 個。

**為什麼不中途停**：每 20 筆停下來記錄的話，120 次只是「連續 20 筆」做 6 遍，測不出連續壓力。

單筆動作沿用正式版本的設定：
- **光耦**：每次按壓 120 ms。
- **RF**：24 bit 代碼，重送 2 次，送出後再等 250 ms 讓接收端判定「放開」。一筆約 340 ms。

測試版韌體拿掉了正式版的 800／1000 ms 冷卻時間。指令間隔由測試條件決定；A 送法另外包含電腦和 Arduino 之間的傳輸時間。

## 需要的東西

**軟體**
- Unity **6000.6.10f1**。專案已設定 API Compatibility 為 .NET Framework、Input Handling 為 Both。
- Arduino IDE。RF 版另外需要 [rc-switch](https://github.com/sui77/rc-switch) 函式庫，開發時用的是 2.6.4 版。

**硬體**
- Arduino Nano V3.0（ATmega328P）。兩種入口各燒一塊，或同一塊輪流燒錄。
- 光耦電路，接到跑步機面板按鍵。
- 433 MHz RF 發射模組。
- 跑步機：XTERRA DT168，速度範圍 1.0～6.0 km/h（最高 6.0 是實測確認）。

## 快速開始

1. 把專案 clone 下來，用 Unity Hub 加入專案，以 6000.6.10f1 開啟。
2. 把 `Arduino/StressTest_Opto` 或 `Arduino/StressTest_RF` 燒錄到 Nano（見下一節）。
3. 在 Unity 開啟 `Assets/Scenes/StressTest.unity`，按 **Play**。測試介面會自動出現，不需要手動掛任何元件。
4. 在左側選擇入口和 COM port，按「連線」。狀態燈變成綠色就可以開始。
5. 在右側面板最上方確認送法是「**A 等回覆**」（正式實驗）。
6. 先架好手機錄影。接下來每一步照[操作流程](#操作流程)的步驟 0～12 做。

> 第一次正式測試前，建議先照 [Docs/BenchAcceptance.md](Docs/BenchAcceptance.md) 做一次台架驗收和前測。

## 硬體接線與燒錄

| 韌體 | 腳位 | 用途 |
|---|---|---|
| `StressTest_Opto` | D3 | 加速 |
| | D4 | 減速 |
| | D5 | 停止 |
| | D6 | 啟動 |
| `StressTest_RF` | D10 | RF 發射（TX） |

> 韌體 v0.5.0 加入 A 送法需要的 `ZERO`、`CMD`、`STAT`。**兩塊板子都要重新燒錄**；舊韌體連得上，但程式會拒絕開始 A 送法的輪次。

**燒錄設定**
- 開發板選「Arduino Nano」，處理器選「ATmega328P」。上傳失敗的話改選「ATmega328P (Old Bootloader)」。
- 序列埠 baud 是 **115200**。燒錄完成後，用序列埠監控視窗（行尾選「Newline」）應該會看到：
  - 光耦版：`READY,OPTO,0.5.0,press_ms=120;action_ms=120;max_run=90;ack=1`
  - RF 版：`READY,RF,0.5.0,bits=24;repeat=2;release_ms=250;action_ms=340;max_run=90;ack=1`
- **燒錄完記得關掉序列埠監控視窗**，否則 Unity 連線時會顯示「被其他程式占用」。

## 操作流程

下面照 **A 送法**（正式實驗）的順序一步一步說明。每一步分三點：

- **做什麼**：你要動手做的事。
- **看哪裡**：畫面上的文字。
- **怎麼看**：怎樣算正確，不對時怎麼辦。

> 步驟 0～5 的截圖是韌體 0.3.0 時拍的：版面相同，但沒有送法切換，數字也不同，以內文為準。步驟 6 以後是新畫面，還沒有截圖，用文字框畫出畫面上的字。舊畫面的完整截圖在 [Docs/UI-Screens.md](Docs/UI-Screens.md)。

### 先認識畫面

![畫面的三個區域](Docs/screenshots/ui/05_idle.png)

| 位置 | 名稱 | 裡面有什麼 |
|---|---|---|
| 最上面一條 | **狀態列** | 左邊是**圓形燈號**和連線狀態；右邊是「中斷連線」（一輪進行中按不下去）和紅色的「**緊急停止（空白鍵）**」 |
| 左邊大塊 | **「現在要做的事」** | 現在該做的那一件事。**綠色的大按鈕就是下一步要按的** |
| 右邊大塊 | **條件矩陣** | 最上面選送法；下面是 4 種間隔 × 3 種次數，每格寫光耦、RF 各完成幾輪 |

> **安全**：跑帶上和後方不要有人或東西。任何時候覺得不對勁，按鍵盤的**空白鍵**緊急停止。跑步機沒有反應，直接按跑步機本體的停止鍵。

### 步驟 0：開始前的準備（不用開程式）

**做什麼**
1. 把要測的入口韌體燒到 Nano：測光耦燒 `Arduino/StressTest_Opto`，測 RF 燒 `Arduino/StressTest_RF`。燒錄方法見[硬體接線與燒錄](#硬體接線與燒錄)。
2. **關掉 Arduino IDE 的序列埠監控視窗。** 沒關的話，程式會連不上。
3. 把 Nano 的 USB 線接到電腦，跑步機插電。
4. **跑帶上不要站人**，跑步機本體的停止鍵要放在你伸手按得到的地方。
5. 架好手機錄影，畫面要**同時拍到跑步機面板和電腦螢幕**。之後懷疑某一段的結果時，可以回頭看。

### 步驟 1：開啟測試程式

![尚未連線](Docs/screenshots/ui/01_disconnected.png)

**做什麼**：在 Unity 開啟 `Assets/Scenes/StressTest.unity`，按上方的 **Play** ▶；如果用的是建置好的執行檔，直接雙擊 `StressTest.exe`。

**看哪裡**：狀態列左上角的燈號，以及左邊「現在要做的事」。

**怎麼看**：燈號是**灰色**，旁邊寫「尚未連線」；左邊顯示「連線到 Arduino」。看到這個畫面就是正常的。

---

### 步驟 2：連線到 Arduino

**做什麼**
1. 左邊「**1. 選擇入口**」：測光耦按「光耦」，測 RF 按「RF」。**必須和板子上燒的韌體一致。**
2. 「**2. 選擇 COM port**」：按 Nano 所在的 COM port，例如 `COM3`。列表是空的，就按右邊的「重新整理」。
3. 按綠色的「**3. 連線**」。

**看哪裡**：狀態列的燈號和燈號旁邊的文字。

**怎麼看**
- 燈號先變**黃色**，顯示「等待韌體回報身分…」，大約 2 秒。這是 Nano 正在重開機，屬於正常現象。
- 接著變**綠色**，顯示「已連線：光耦韌體 v0.5.0」（或 RF），下方小字是韌體參數。**看到綠燈就成功了**，畫面會變成步驟 3 的樣子。

**連不上時：**

| 畫面 | 燈號／文字 | 原因 | 怎麼處理 |
|---|---|---|---|
| ![入口不符](Docs/screenshots/ui/02_entry_mismatch.png) | 🔴「入口不符：選了光耦，板子是 RF 韌體」 | 選的入口和板子上的韌體不一樣 | 按左邊的「中斷連線，重新選擇」，改選正確的入口，或換一塊板子 |
| ![連線逾時](Docs/screenshots/ui/04_handshake_timeout.png) | 🔴「逾時：4 秒內沒有收到韌體回報」 | 板子上不是測試韌體，或 baud 不對 | 重新燒錄測試韌體，再連一次 |
| （紅字顯示在左邊） | 「COM3 被其他程式占用」 | 序列埠監控視窗還開著 | 關掉 Arduino IDE 的序列埠監控視窗，再按連線 |

### 步驟 3：選送法和條件

![已連線、閒置](Docs/screenshots/ui/05_idle.png)

**做什麼**
1. 右側面板最上方選「**A 等回覆**」。
2. **架好手機**，畫面要拍得清楚跑步機面板的數字。
3. 看清楚左邊的條件，按綠色的「**開始下一輪**」。

**看哪裡**

```
下一輪（A）：光耦、間隔 0 ms、120 次
加速 60 次、減速 60 次，分 6 段（每段 20 筆），每段換方向、中間不停
第 1 輪。開始後會自動啟動跑步機（開機 1.0 km/h），預熱加速 15 次到 2.5 後開始計分（2.5↔4.5）。跑帶上請不要站人。
請先架好錄影。送完後要輸入最後速度，再看影片輸入 5 個轉向點。
[ 開始下一輪 ]
```

**怎麼看**
- 入口要和接上的板子一致。條件由系統照排程選好；想指定條件，就按右邊矩陣的格子。
- 矩陣的「光耦 1/3」代表這個條件光耦完成 1 輪，目標 3 輪。

### 步驟 6：確認起點，開始錄影

**做什麼**
1. 看面板，輸入現在的速度（例如 `2.5` 或 `25`），按 **Enter**。
2. **按下手機的錄影。**
3. 再按 **Enter**，指令立刻開始連續送出。

**看哪裡**

```
你輸入的面板速度：2.5 km/h
確認後會連續送出 120 筆，中間不停。請先開始錄影，畫面要拍到跑步機面板。
[ 已開始錄影，開始送出（Enter） ]  [ 修改輸入（Esc） ]
```

**怎麼看**：打錯按 **Esc** 重打。面板不是 2.5 時會多一個畫面：
- 「**重新預熱（補足差額）**」（建議）：系統補按差的次數，再確認一次。
- 「**以 2.3 為起點繼續**」：立刻開始送出，**先開錄影**。

---

### 步驟 7：連續送出中（不要操作）

**看哪裡**

```
本輪（A）：間隔 0 ms、120 次，中間不停　段 3／6
連續送出中：第 3／6 段（加速）
已送 45／120 筆、已回覆 44 筆
[進度條]
速度在 2.5 和 4.5 之間來回。現在不用操作，確認手機正在錄影。
```

**怎麼看**
- 面板速度會上上下下。段數會自己往前走。
- 120 次大約：光耦 15 秒以上，RF 41 秒以上（推算值）。
- 「已回覆」停住幾秒，代表有指令沒回覆；程式逾時後繼續，連續 3 筆沒回覆就提早結束整次傳送。沒送完的輪次會**自動作廢**，只需要輸入有送出的段。
- 有異狀按**空白鍵**。這一輪會作廢，逐筆紀錄仍保留。

---

### 步驟 8：輸入最後速度，程式停止跑步機

**做什麼**：看面板，等數字不再變，輸入，按 **Enter**；確認後再按一次 **Enter**。

**看哪裡**

```
整輪送完了，跑步機還在轉。
請看面板，現在的速度（預期 2.5）
[ 輸入框 ]  [ 確認（Enter） ]
確認後程式會停止跑步機。
```

```
最後速度：2.4 km/h
[ 確認，停止跑步機（Enter） ]  [ 修改輸入（Esc） ]
```

**怎麼看**
- 有指令沒回覆或 Arduino 重開機時，上方會出現「注意」。照面板輸入。重開機的那一輪之後要作廢。
- 按下確認後跑步機停止。可以停止錄影。
- 確認後才發現打錯：在步驟 9 或 10 一直按 **Esc** 退回「修改最後速度（跑步機已停止）」，改完不會再送停止。
- 如果停止指令沒有回覆，步驟 9 會出現提醒：確認跑帶已停，沒停就按跑步機上的停止鍵。讀數照常輸入。

---

### 步驟 9：看影片，輸入轉向點

**做什麼**
1. 回放影片。
2. 照畫面指示找第幾段結束時的**最高點**或**最低點**。
3. 輸入數字，按 **Enter**。畫面自動換下一個。

**看哪裡**

```
看錄影：轉向點 1／5
找第 1 段（加速）結束、換方向時面板的最高點。跑步機已停，可以慢慢看。
最後速度 2.4　已輸入：（還沒有）
最高點（預期 4.5）
[ 輸入框 ]  [ 確認（Enter） ]
[ 回上一個（Esc） ]  [ 讀不到，作廢此輪 ]
看不清楚時不要猜。輸入完之前不要關程式。
```

**怎麼看**
- 「預期」是用上一個讀數推算的，**照影片上看到的數字輸入**，不要照預期填。
- 打錯：按 **Esc** 回上一個。
- 看不清楚：按「**讀不到，作廢此輪**」。逐筆紀錄和電腦端筆數仍保留。
- 就算拔掉 USB，已輸入的數字也還在。**關掉程式會丟掉讀數**（逐筆紀錄和整輪筆數仍會寫入，記為作廢）。

---

### 步驟 10：核對各段結果

**看哪裡**

```
請核對各段結果
段 1：加速 20 筆，2.5 → 4.3，掉包 2（序列端少 0、跑步機端少 2）
段 2：減速 20 筆，4.3 → 2.4，掉包 1（序列端少 0、跑步機端少 1）
[ 確認，完成本輪（Enter） ]  [ 修改輸入（Esc） ]
[ 讀不到，作廢此輪 ]
```

（這個例子是 40 次，共 2 段。）

**怎麼看**
- 每一段從**上一個實際讀數**算起。第 1 段從起點 2.5 算。
- **序列端少**：電腦送了，Arduino 沒收到。**跑步機端少**：Arduino 做了，面板沒跟著動。顯示「不明」代表無法分到各段，整輪合計在下一個畫面。
- 沒問題按 **Enter**，各段寫進紀錄。打錯按 **Esc**。

---

### 步驟 11：看本輪總結，離開這一輪

**做什麼**
1. 確認跑帶**完全停下來**。
2. 沒問題：按「**跑帶已停止，回到設定**」。
3. 有問題（看錯面板、有人碰到跑步機、重開機、出現「可能觸底／觸頂」）：在「作廢原因」寫原因，按「**作廢此輪**」。指令遺失**不是**作廢理由。

**看哪裡**

```
本輪完成：總掉包 3／40 筆
段 1：加速 20 筆，2.5 → 4.3，掉包 2（序列端少 0、跑步機端少 2）
段 2：減速 20 筆，4.3 → 2.4，掉包 1（序列端少 0、跑步機端少 1）
各段合計：電腦送 40、Arduino 收 40、執行 40；序列端少 0、跑步機端少 3
實際間隔：平均 … ms、最大 … ms
加速：預計 20、Arduino 實送 20　減速：預計 20、Arduino 實送 20　預熱（不計分）：加速 15、減速 0
紀錄位置：…
請確認跑帶已完全停止，再開始下一輪。
作廢原因 [        ]  [ 作廢此輪 ]
[ 跑帶已停止，回到設定 ]
```

**怎麼看**：一定要按其中一顆按鈕，這一輪才會寫進 `rounds` 紀錄、算進矩陣進度。

### 步驟 12：跑下一輪，或換板子

回到步驟 3。左邊出現「依整體排程下一輪輪到 RF（或光耦）」時，可以按「中斷連線」換板子，回到步驟 2。右邊矩陣下次開程式時會從紀錄檔讀回來。只有整輪不停的 A 紀錄算進 A 的進度。

### RUN 對照的流程

右側面板選「RUN 對照」。和上面不同的地方：

1. 起點 2.0、預熱 10 次；起點確認後直接開始第 1 段。
2. 每送完一段就停下來：畫面顯示「請看面板，預期 4.0 km/h」，輸入後顯示「面板 3.7 km/h → 推算掉包 3 筆」，按 Enter 開始下一段。
3. 最後一段確認後停止跑步機，顯示總結。不需要看影片找轉向點。

### 遇到緊急或異常狀況

| 什麼情況 | 畫面 | 怎麼處理 |
|---|---|---|
| 按了空白鍵或紅色「緊急停止」（送出中） | 「緊急停止：等 Arduino 中止…」 | 系統停止送指令並停止跑步機。**2 秒內跑帶沒停，按跑步機上的停止鍵。** 這一輪作廢 |
| 確認最後速度之後按到空白鍵 | 畫面不變 | 只會再送一次停止，這一輪**不**作廢 |
| 一輪進行中拔掉 USB 或關掉程式（確認最後速度之前） | 「連線中斷，本輪記為作廢…」 | **跑步機可能還在轉**，程式只能盡量送停止。確認並按跑步機上的停止鍵。逐筆紀錄有保存 |
| A 送法沒送完就結束（連續 3 筆沒回覆、重開機） | 「沒有送完全部指令，這一輪會自動作廢」 | 照畫面輸入有送出的段，供查原因 |
| 測試中途出錯 | 「本輪中斷：…」 | 看原因，確認跑步機停下，按「回到設定」。這一輪作廢 |
| RUN 對照某段太久沒回報 | 提示逾時 | 照面板輸入；系統最多再等 30 秒，然後開始下一段 |

### 手動工具（硬體檢查用）

![手動工具](Docs/screenshots/ui/06_idle_manual_tools.png)

**做什麼**：在步驟 3 的畫面按「**展開手動工具（單發、手動單段）**」。

**用途**
- **單發測試**：按「啟動」「加速」「減速」「停止」，各送一次指令，用來確認接線和跑步機有沒有反應。例如按「加速」，面板應該 +0.1。
- **手動單段**：自己選方向（加速／減速）、間隔（0 ms～1 s）、筆數，再填「目前面板速度」，按「跑一段」。送法跟右側面板的選擇一致；筆數上限 A 為 300、RUN 為 90。跑完後輸入一次面板速度，不需要看影片找轉向點。

手動工具的結果另外存在 `manual_segments_*.csv`，**不計入矩陣進度**，可以放心拿來前測或排除問題。

## 紀錄檔（CSV）

紀錄檔是程式幫你記下的表格，可以直接用 Excel 打開。位置在專案資料夾的 `TestLogs/`，右側面板的「開啟紀錄資料夾」按鈕可以直接打開。

### 想知道什麼，就開哪個檔

| 你想知道 | 開這個檔 | 一列是什麼 |
|---|---|---|
| 哪一段掉了指令、掉在哪裡（**最常用**） | [`segments_*.csv`](#segments每一段) | 一段（例如加速 20 筆） |
| 哪一輪可以用、整輪掉了多少 | [`rounds_*.csv`](#rounds每一輪) | 一輪 |
| 某一筆指令發生什麼事 | [`commands_*.csv`](#commands逐筆指令) | 一筆指令 |
| 手動工具跑的結果 | [`manual_segments_*.csv`、`manual_commands_*.csv`](#manual_segments手動單段) | 手動跑的一段、一筆指令 |

### 什麼時候存檔

- **A 送法**：整輪送完（或緊急停止）的當下，`commands` 先寫入整輪的逐筆紀錄；核對畫面按確認後，`segments` 寫入各段。
- **RUN 對照**：你按 Enter 確認一段的讀數時，那一段寫進 `segments` 和 `commands`。
- 你在總結畫面或中斷畫面按按鈕離開時，那一輪寫進 `rounds`。
- 寫一列就存一列。Unity 當掉也不會弄丟已經確認的段。
- 每次執行程式，第一次開始輪次時會開一組新檔，檔名有日期時間。手動工具的檔案在第一次輸入手動讀數時才開。

以下情況**不會**留下紀錄：

- RUN 對照中被緊急停止打斷、或還沒按 Enter 確認的段。
- A 送法中按「讀不到，作廢此輪」、緊急停止，或沒按完確認時，`segments` 沒有那一輪（`commands` 和 `rounds` 仍有）。
- 當機或強制結束程式時，進行中那一輪的資料可能沒寫入。正常關閉程式或拔掉 USB 時，這一輪會寫進 `rounds` 並記為作廢。

### 看檔案前先知道

| 看到 | 意思 |
|---|---|
| `1`、`0` | 是、否 |
| 空白 | 沒有這個值 |
| 速度 | 單位是 km/h，寫到小數一位 |
| 欄名結尾是 `_us` | 時間，單位是微秒。`1000` 等於 1 毫秒（ms），`5008` 大約是 5 ms |
| `entry` | `OPTO`＝光耦，`RF`＝RF |
| `direction` | `UP`＝加速，`DOWN`＝減速 |
| `send_mode` | `A`＝等回覆，`RUN`＝對照 |
| `flow` | `continuous`＝整輪不停（A），`segmented`＝每段停下來（RUN、手動段） |
| `segment_index` | 這一輪的第幾段，**從 0 數起**：0 加速、1 減速、2 加速、3 減速，依此類推 |
| `round_id` | 輪次的名字。三種檔案用它互相對照 |

`round_id` 的讀法，以 `20261127-143000-OPTO-A-G5-N80` 為例：

```
20261127  143000    OPTO   A      G5        N80
日期      開始時間   光耦   A 送法  gap 5 ms  總共 80 次
```

### 一個例子

這是示範數字，不是實測結果。A 送法，加速段 20 筆，起點 2.5。有 1 筆在傳輸途中不見了，轉向點的面板最高到 4.2。

| 欄位 | 值 | 怎麼讀 |
|---|---|---|
| `count` | 20 | 應該送 20 筆 |
| `start_speed` → `expected_end` | 2.5 → 4.5 | 全部成功的話，要到 4.5 |
| `actual_end` | 4.2 | 面板實際最高到 4.2 |
| `pc_sent` | 20 | 電腦送了 20 筆 |
| `arduino_received` | 19 | Arduino 只收到 19 筆 |
| `arduino_executed` | 19 | Arduino 做了 19 筆 |
| `panel_steps` | 17 | 面板只動了 17 格 |
| `link_lost` | 1 | **序列端少 1**（20 − 19） |
| `treadmill_missing` | 2 | **跑步機端少 2**（19 − 17） |
| `drops` | 3 | 總共少 3 格（4.5 和 4.2 差 0.3） |
| `no_reply` | 1 | 有 1 筆沒有回覆 |
| `report_short` | 1 | 提醒：有指令沒有完成往返 |

### segments：每一段

分析掉包主要看這個檔。下面按用途分組，順序和檔案裡的欄位順序不同。

**這是哪一段**

| 欄位 | 意思 |
|---|---|
| `recorded_at` | 你確認這段讀數的時間 |
| `round_id` | 哪一輪 |
| `segment_index` | 第幾段（從 0 數起） |
| `entry` | 光耦或 RF |
| `send_mode` | 送法 |
| `flow` | 整輪不停或每段停下 |
| `direction` | 加速或減速 |
| `count` | 這段**應該**送幾筆（正常是 20） |
| `gap_ms` | 設定的等待時間（毫秒） |
| `firmware_version` | Arduino 程式的版本 |

**掉了多少、掉在哪**

| 欄位 | 意思 |
|---|---|
| `link_lost` | **序列端少**：電腦送了，Arduino 沒收到的筆數。只有 A 送法有 |
| `treadmill_missing` | **跑步機端少**：Arduino 做了，面板沒跟著動的格數。**負數**代表面板動得比指令多 |
| `drops` | **推算掉包**：面板和「應該到的速度」差幾格。多動和少動都算正數。算法見[掉包怎麼算](#掉包怎麼算) |
| `panel_steps` | 面板朝指令方向動了幾格（一格 0.1）。反方向是負數 |

**面板速度**

| 欄位 | 意思 |
|---|---|
| `start_speed` | 這段開始時的速度。第一段是預熱後你確認的讀數，之後是上一段的 `actual_end` |

| `actual_end` | 這段結束時的面板速度。A：轉向點讀數（看影片），最後一段是送完當下的讀數。RUN：每段停下來讀的值 |
| `expected_end` | 全部成功時應該到的速度。這是算出來的，可能超出跑步機的範圍 |
| `expected_change` | 應該變多少。加速是正數，減速是負數 |
| `actual_change` | 實際變多少（`actual_end` − `start_speed`） |

**各處數到幾筆**

| 欄位 | 意思 |
|---|---|
| `pc_sent` | 電腦送出幾筆（A） |
| `arduino_received` | Arduino 收到幾筆完好的指令（A） |
| `arduino_executed` | Arduino 做完幾筆（A） |
| `arduino_bad` | Arduino 收到幾行壞掉或看不懂的內容（A） |
| `replies` | 電腦收到幾個「做完了」，晚到的也算（A） |
| `no_reply` | 幾筆沒有回覆（A） |
| `rejected` | 幾筆被 Arduino 回報內容壞掉（A） |
| `reported_count` | Arduino 說它做了幾筆。A：等於 `arduino_executed`，問不到時用 `replies`。RUN：段結束時的回報，逾時就空白 |

標（A）的欄位和 `link_lost`，在 RUN 對照是空白。A 送法問不到 Arduino 的計數時，`arduino_*`、`link_lost`、`treadmill_missing` 也是空白。

A 送法的 Arduino 計數是整輪合計。程式只在分得清楚時才分給各段（沒回覆的指令全都沒做，或全都做了）；同一輪混有指令遺失和回覆遺失時，各段的 `arduino_*`、`link_lost`、`treadmill_missing` 空白，請看 `rounds` 的整輪數字。

**這段能不能用**

| 欄位 | `1` 代表 | 怎麼處理 |
|---|---|---|
| `possibly_clamped` | 應該到的速度低於 1.0 或高於 6.0，跑步機到底或到頂了 | 這段的 `drops`、`treadmill_missing` **不能用** |
| `report_short` | 有指令沒有完成：沒回覆、回報筆數不夠、逾時或重開機 | A：這是要分析的掉包資料。RUN：這段要排除 |
| `timed_out` | 等太久，段提早結束。A：連續 3 筆沒有準時回覆。RUN：整段沒有回報完成 | 看原因 |
| `rebooted` | Arduino 在這段重開機 | 那一輪要作廢，紀錄留著查原因 |

**實際停多久**

| 欄位 | 意思 |
|---|---|
| `mean_gap_us` | 這段兩筆指令之間，實際停的時間平均值。算不出來時是 `0.0` |
| `max_gap_us` | 實際停最久的一次。算不出來時是 `0` |

### rounds：每一輪

先看 `status`：只有 `completed` 的輪次可以算掉包率。右側矩陣的進度也是從這個檔讀回來的。

**這是哪一輪**

| 欄位 | 意思 |
|---|---|
| `recorded_at` | 寫入這一列的時間（你離開總結畫面時） |
| `round_id` | 輪次的名字 |
| `entry` | 光耦或 RF |
| `send_mode` | 送法 |
| `flow` | 整輪不停（`continuous`）或每段停下（`segmented`） |
| `gap_ms` | 設定的等待時間（毫秒） |
| `total_count` | 整輪計畫送幾筆（40／80／120） |
| `segment_size` | 每段幾筆（正常 20） |
| `firmware_version` | Arduino 程式的版本 |
| `firmware_params` | Arduino 回報的設定，用分號隔開，例如按壓時間 `press_ms=120` |

**能不能用**

| 欄位 | 意思 |
|---|---|
| `status` | `completed`＝可以分析。`voided`＝作廢（你按作廢、緊急停止，或中途出錯） |
| `void_reason` | 作廢原因。逗號會換成全形 |
| `segments` | 完成幾段。跑完時：40 次是 2 段、80 次 4 段、120 次 6 段 |
| `any_possibly_clamped` | `1`＝至少一段到底或到頂 |
| `any_report_short` | `1`＝至少一段有指令沒有完成 |
| `any_rebooted` | `1`＝至少一段重開機 |

**掉了多少**

| 欄位 | 意思 |
|---|---|
| `link_lost` | 各段「序列端少」加總（A） |
| `treadmill_missing` | 各段「跑步機端少」加總，**包含**到底或到頂的段 |
| `total_drops` | 各段「推算掉包」加總，**包含**有提醒的段 |

A 送法的合計直接用整輪的 Arduino 計數。轉向點沒輸入（作廢）時 `treadmill_missing` 空白；RUN 對照任一段不明時合計空白。

**筆數**

| 欄位 | 意思 |
|---|---|
| `total_sent` | 已完成的段**應該**送幾筆。名字有 sent，但**不是**實際送出數 |
| `pc_sent` | 電腦實際送出幾筆（A） |
| `arduino_received` | Arduino 收到幾筆（A） |
| `arduino_executed` | Arduino 做完幾筆（A） |
| `arduino_bad` | Arduino 收到幾行壞掉或看不懂的內容（A） |
| `up_planned` | 計畫加速幾筆（正常是總次數的一半） |
| `down_planned` | 計畫減速幾筆（正常是總次數的一半） |
| `up_sent` | Arduino 回報加速做了幾筆（RUN 逾時的段算 0） |
| `down_sent` | Arduino 回報減速做了幾筆（RUN 逾時的段算 0） |

**起點、終點和預熱**

| 欄位 | 意思 |
|---|---|
| `warmup_reading` | 開始算分前，你確認的面板速度（正常 A 是 2.5、RUN 是 2.0）。還沒到這步就中斷時空白 |
| `end_reading` | 最後一段結束時的面板速度；沒有各段結果時空白 |
| `warmup_up` | 預熱按了幾次加速。正常 A 是 15、RUN 是 10。不算分 |
| `warmup_down` | 重新預熱時按了幾次減速。正常是 0。不算分 |

**實際停多久**

| 欄位 | 意思 |
|---|---|
| `mean_gap_us` | 整輪指令之間實際停的時間平均值（不含你看面板的時間） |
| `max_gap_us` | 整輪停最久的一次 |

### commands：逐筆指令

要查某一筆指令發生什麼事、或實際停多久時看這個檔。它**看不出跑步機有沒有收到**某一筆。

- A 送法：電腦送出的每一筆都有一列，沒回覆的也有。
- RUN 對照：只有 Arduino 有回報時間的指令才有列。整段逾時時，一列都沒有。

**是哪一筆**

| 欄位 | 意思 |
|---|---|
| `round_id` | 哪一輪 |
| `entry` | 光耦或 RF |
| `send_mode` | 送法 |
| `gap_ms` | 設定的等待時間（毫秒） |
| `total_count` | 整輪計畫幾筆。手動段是這一段填的筆數 |
| `segment_index` | 第幾段（從 0 數起） |
| `seq` | 這段的第幾筆（從 0 數起） |
| `cmd_seq` | 指令的流水號，連線期間一直增加（A） |
| `direction` | 加速或減速 |

**結果**

| 欄位 | 意思 |
|---|---|
| `status` | 只有 A 送法有，值見下表 |

| `status` 的值 | 意思 |
|---|---|
| `done` | 準時回覆「做完了」 |
| `late` | 超過時間才回覆 |
| `rejected` | Arduino 說收到的內容壞掉，沒有做 |
| `no_reply` | 一直沒回覆。可能沒收到，也可能回覆不見了。要看 `segments` 的計數才分得出來 |
| `pending` | 還沒等到回覆，這段就結束了（例如重開機） |

**時間**

| 欄位 | 誰記的 | 意思 |
|---|---|---|
| `rx_us` | Arduino | 讀到這筆指令的時間（A） |
| `start_us` | Arduino | 開始動作的時間 |
| `end_us` | Arduino | 動作做完的時間。光耦：放開按鍵之後。RF：發射完再等 250 ms 之後 |
| `gap_us` | 計算 | 上一筆做完到這一筆開始，實際停多久。A 換方向那一筆也算得出來；整輪第一筆和缺上一筆資料時空白 |
| `pc_send_us` | 電腦 | 送出這筆指令的時間（A） |
| `pc_reply_us` | 電腦 | 收到回覆的時間，沒回覆時空白（A） |

時間怎麼用：

- 動作花多久 ＝ `end_us` − `start_us`。光耦約 120000，RF 約 340000（推算值，以實測為準）。
- 一來一回花多久 ＝ `pc_reply_us` − `pc_send_us`。
- 電腦和 Arduino 各用自己的時鐘，**兩邊的時間不能互相相減**。
- Arduino 的時鐘約每 71.6 分鐘歸零一次。`gap_us` 已經處理好；自己相減得到負數時，加上 4294967296。
- 沒回覆的列，`rx_us`、`start_us`、`end_us` 空白。

### manual_segments：手動單段

手動工具的結果，**不算進矩陣進度**，可以拿來做前測。

- `manual_segments_*.csv`：欄位和 `segments` 一樣。`round_id`、`segment_index` 空白。`start_speed` 是你填的「目前面板速度」。
- `manual_commands_*.csv`：欄位和 `commands` 一樣。`round_id`、`segment_index` 空白。`total_count` 是你填的筆數。

### 整理論文用的掉包表

用 `segments` 檔，因為它分得出加速、減速，也能挑掉不能用的段。

1. 打開所有 `rounds` 檔，記下 `status` 是 `completed` 的 `round_id`。
2. 把所有 `segments` 檔貼在同一張工作表，只留步驟 1 的那些輪次。
3. 挑掉不能用的資料，並記下挑掉幾段：
   - `possibly_clamped` 是 1：不用它的 `drops`、`treadmill_missing`。
   - RUN 對照且 `report_short` 是 1：整段不用。
   - A 送法的 `link_lost`、`rejected`、`no_reply` 全部保留。
4. 做樞紐分析表：
   - 列：`send_mode`、`entry`、`gap_ms`
   - 欄：`direction`
   - 值：`link_lost`、`treadmill_missing`、`pc_sent`、`arduino_executed`、`reported_count` 的加總
   - 要比較不同總次數時，把 `rounds` 的 `total_count` 用 `round_id` 對過來
5. 算比例。分母要對：

| 要算 | 公式 |
|---|---|
| 序列端掉包率（A） | `link_lost` ÷ `pc_sent` |
| 跑步機端掉包率（A） | `treadmill_missing` ÷ `arduino_executed` |
| 跑步機端掉包率（RUN） | `treadmill_missing` ÷ `reported_count` |

`drops` 是用預定的筆數算的。A 送法只有送滿（`pc_sent` 等於 `count`）的段才能用它。保留每一輪的數字，不要只併成一個總比例。分析原則見[實驗設計第 8 節](Docs/ExperimentDesign.md#8-整理數據的規則)。

> `TestLogs/` 是實驗資料，目前沒有加進 `.gitignore`。要不要放進版本控制，請照研究室的資料管理方式決定。

## 掉包怎麼算

A 送法看兩個數字：**序列端少**（`link_lost`）和**跑步機端少**（`treadmill_missing`），意思見[實驗在做什麼](#實驗在做什麼)。另外有一個由面板直接推算的數字：

```
推算掉包數 = | 預期變化 − 面板實際變化 | ÷ 0.1   （四捨五入）
```

- **預期變化**：方向 × 筆數 × 0.1 km/h。
- **實際變化**：這段結束時的讀數減去這段開始時的讀數。每段的起點用上一段結束時的**實際讀數**，不用理論值，這樣誤差才不會一段段累積下去。A 送法的各段讀數是事後看影片讀的轉向點。

公式取絕對值，所以面板變化**比預期多**（例如一筆指令被跑步機算成兩次，或按住被當成長按連續加速）也會算進 `drops`。要分辨兩者，比較 `|actual_change|` 和 `|expected_change|`：小於是漏反應，大於是多反應。

休息間隔 `gap_ms` 在 RUN 對照是從上一筆**動作結束**起算；A 送法是從**電腦收到完成回覆**起算，實際空檔還要加上序列往返時間，以 `gap_us` 為準。RF 的單筆動作本身包含 250 ms 釋放時間，所以 RF 兩次發射之間的空檔是 250 ms 再加上述空檔；光耦兩次按壓之間腳位為 LOW 的時間就是上述空檔。論文比較兩個入口時需要交代這個差別。

段結果的旗標：

| 旗標 | 意思 |
|---|---|
| `possibly_clamped`（可能觸底／觸頂） | 起點加上預期變化後超出 1.0～6.0 km/h，多出來的指令會被跑步機吃掉，這段推算出來的掉包數不可信。 |
| `report_short`（回報不足） | 回報的筆數少於應送筆數、逾時或重開機。RUN：問題可能出在序列埠或韌體。A：有指令沒有完成往返，是掉包資料。 |
| `timed_out` | RUN：在「筆數 ×（單筆動作時間 + 間隔）× 2 + 2 秒」內沒有收到 `DONE`。A：連續 3 筆沒有準時回覆。 |

Arduino 用 `micros()` 記錄每一筆的開始和結束時間。RUN 對照先把時間戳存在 RAM，整段跑完才一次回傳，執行期間不輸出任何序列資料，避免傳輸時間把間隔拉長；A 送法每做完一筆就回覆一行。

& "<Unity 安裝路徑>\6000.6.10f1\Editor\Unity.exe" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults results.xml -logFile unity.log

## 序列協定

115200 baud，每行以 `\n` 結尾。兩支韌體使用同一套協定。

| Unity → Arduino | 意義 |
|---|---|
| `HELLO` | 要求韌體回報身分 |
| `ONE,<START\|UP\|DOWN\|STOP>` | 單發一次 |
| `RUN,<UP\|DOWN>,<n>,<gap_ms>` | 連續送 n 筆（n ≤ 90）；每筆動作完成後休息 gap_ms 毫秒 |
| `ABORT` | 中止執行中的 RUN |
| `ZERO` | 逐筆計數歸零（每次傳送開始時；A 送法一輪一次） |
| `CMD,<seq>,<UP\|DOWN>*XX` | 逐筆指令：做一筆，做完回 `X` |
| `STAT` | 查詢逐筆計數 |

| Arduino → Unity | 意義 |
|---|---|
| `READY,<OPTO\|RF>,<版本>,<參數>` | 開機時或回應 HELLO；參數的 `max_run` 是單次 RUN 的筆數上限 |
| `ACK,<原指令>` | 已接受指令 |
| `T,<i>,<start_us>,<end_us>` | 第 i 筆的開始與結束時間；整段跑完後才一次送出 |
| `DONE,<n>` | RUN 完成 |
| `ABORTED,<n>` | RUN 被中止，n 為中止前已完成的筆數 |
| `ERR,<原因>` | 例如 `BAD_COMMAND`、`BAD_RUN`、`BUSY`（RUN 執行期間收到其他指令）、`UNKNOWN` |
| `X,<seq>,<rx_us>,<start_us>,<end_us>*XX` | 逐筆指令的完成回覆 |
| `NAK,BAD_LINE*XX` | `CMD` 行毀損，沒有執行 |
| `STAT,<收到>,<執行>,<毀損>*XX` | 回應 `STAT` |

`*XX` 是 `*` 之前所有位元組 XOR 的兩位大寫十六進位，例如 `CMD,1,UP*7E`。

### A 送法的收送規則

一次傳送的順序（A 送法一輪只有一次，換段換方向不停；手動段一段一次）：

```
ZERO → ACK,ZERO → （CMD → X → 等 gap）重複 n 次 → STAT → STAT,收到,執行,毀損
```

| 情況 | 程式怎麼做 |
|---|---|
| 序號 | 連線期間一直增加，不重複，遲到的回覆不會配錯 |
| 指令沒有回覆 | 超過「2 × 單筆動作時間 + 1 秒」記為 `no_reply`，送下一筆。**不重送** |
| 連續 3 筆沒有準時回覆 | 提早結束整次傳送。遲到的回覆不會讓計數歸零 |
| 逾時後回覆才到 | 這一段還沒結束時記為 `late` |
| Arduino 回 `NAK` 或 `ERR` | 正在等回覆的那一筆記為 `rejected`，至少等 50 ms 再送下一筆 |
| `ZERO`、`STAT` 沒有回覆 | 最多問 3 次（不影響跑步機）。仍問不到時，Arduino 計數留空 |
| 傳送中或等讀數時 Arduino 重開機 | 標記 `rebooted`；傳送中會結束整次傳送。A 送法確認最後速度之後就不再偵測 |
| `STAT` 的數字比收到的完成回覆少 | 代表計數中途歸零，Arduino 計數留空 |

電腦端用獨立執行緒收送，間隔不受畫面更新率限制。

## 已知限制

- **A 送法的實際空檔比 gap 長**：多出傳輸時間（尚未實測），可能蓋掉 0／1／5／10 ms 的差別。先做前測 T2。
- **光耦可能被當成長按**（推測，未實測）：兩次按壓之間放開時間很短時，面板可能看不到放開。做前測 T6。
- **RUN 對照的 RF 間隔差異很小**：每筆固定有 250 ms 釋放時間，gap 0 到 10 ms 的差別相對很小。
- **量不到模組輸出**：跑步機端少掉的指令，分不出是光耦／RF 模組還是跑步機造成。
- **部分重開機偵測不到**：Arduino 在回覆任何指令之前重開，而且開機訊息遺失時，程式不會發現。
- **以段為單位判定**：跑步機本身不會回報收到哪一筆指令，只能從每段的面板讀數推算。如果同一段裡同時「漏一筆」又「多一筆」，兩者會互相抵銷，看不出來。要逐筆核對只能看錄影。
- **RF 的 `action_ms=340` 是推算值**：由 frame 長度和釋放時間算出，只用於估計逾時和顯示進度條。實際耗時請看 CSV 裡的時間戳，並在台架驗收時填入實測值。
- **面板輸入的規則**：沒有小數點、且數值 ≥ 10 的整數會自動除以 10（例如 `27` → 2.7、`60` → 6.0）。只接受 1.0～6.0。
- **偏移累積太多時無法判讀**：理論終點超出 1.0～6.0 的段會標記 `possibly_clamped`。A 從 2.5 起，上下各 15 格；RUN 從 2.0 起，往下 10 格。
- **轉向點靠看影片**：面板更新比指令慢時，讀到的最高點可能偏低，看起來像掉包。正式測試前先做 T0。畫面上的預期值可能影響讀數。
- **輸入轉向點時不要關程式**：讀數在按下最後確認前只在記憶體裡。
- **最高速度 6.0**：每段上限 A 為 35 筆（2.5 → 6.0）、RUN 為 40 筆（2.0 → 6.0）。程式把 6.0 當成整台跑步機的上限，兩種入口相同。
- **預熱結果可能差 1 格**：實機曾出現送 10 次停在 1.9，原因未確認；改送 11 次後停在 2.1，所以維持 10 次。再出現 1.9 時用「重新預熱」補差額，並記下來。如果跑步機閒置後常吃掉第一下，每段會多 1 筆掉包；台架驗收時請照 D 節檢查。
