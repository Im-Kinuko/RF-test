# RF／光耦 控制入口間隔壓力測試

這個 Unity 專案用來比較跑步機的兩種控制方式：光耦（V1，模擬按壓面板按鍵）和 433 MHz RF（V2，走原廠遙控通道）。測試時連續送出加速、減速指令，改變每筆指令之間的休息間隔，觀察哪一種方式在哪個間隔開始掉包。

Unity 送出測試指令給 Arduino，Arduino 用毫秒級的間隔連續送出。每送完一段，研究人員看跑步機面板、輸入速度，工具就推算出這段漏了幾筆，結果全部寫成 CSV。

> 研究背景：研究問題一，「在相同加減速指令與不同發送間隔下，兩個控制入口能否正確輸出」。外部遙控器監聽（研究問題二）不在本專案範圍內。

## 測試設計

| 項目 | 設定 |
|---|---|
| 控制入口 | 光耦、RF |
| 休息間隔 | 0／1／5／10 ms，從上一筆動作**完成後**開始計時 |
| 每輪總次數 | 40／80／120 筆 |
| 每段筆數 | 20 筆（可調），加速段和減速段輪流 |
| 速度範圍 | 跑步機開機與最低速度都是 1.0 km/h；預熱到 2.0 後，每段在 2.0 ↔ 4.0 km/h 之間來回，每次按鍵 ±0.1 km/h |
| 加減速次數 | 40 次＝加速 20、減速 20；80 次＝各 40；120 次＝各 60。畫面和每輪 CSV 都會記下預計與實際送出的次數 |
| 重複次數 | 每個條件 3 輪（可調） |
| 條件總數 | 4 種間隔 × 3 種總次數 × 2 種入口 = 24 個條件，共 72 輪 |

**一輪的流程**
1. 送出「啟動」，倒數 5 秒，等跑帶穩定。
2. 預熱：每秒加速 1 次，共 10 次，把速度從開機的 1.0 km/h 帶到 2.0 km/h。這段不計分。起點設在 2.0，是為了和最低速度 1.0 之間留 10 筆的餘裕：上一段漏掉幾筆加速時，減速段才不會先撞到底。
3. 研究人員確認面板顯示 2.0。如果不是 2.0，可以選「重新預熱」（用單發補足差額，不計分），或「以實際速度為起點繼續」。
4. 依總次數分成 2／4／6 段。每段由 Arduino 連續送 20 筆，送完後研究人員輸入面板速度，確認後進入下一段。
5. 送出「停止」，顯示本輪總結。

單筆動作沿用正式版本的設定：
- **光耦**：每次按壓 120 ms。
- **RF**：24 bit 代碼，重送 2 次，送出後再等 250 ms 讓接收端判定「放開」。一筆約 340 ms。

測試版韌體拿掉了正式版的 800／1000 ms 冷卻時間，所以指令間隔完全由測試條件決定。

## 需要的東西

**軟體**
- Unity **6000.6.10f1**。專案已設定 API Compatibility 為 .NET Framework、Input Handling 為 Both。
- Arduino IDE。RF 版另外需要 [rc-switch](https://github.com/sui77/rc-switch) 函式庫，開發時用的是 2.6.4 版。

**硬體**
- Arduino Nano V3.0（ATmega328P）。兩種入口各燒一塊，或同一塊輪流燒錄。
- 光耦電路，接到跑步機面板按鍵。
- 433 MHz RF 發射模組。
- 跑步機：XTERRA DT168，速度範圍 0～12 km/h。

## 快速開始

1. 把專案 clone 下來，用 Unity Hub 加入專案，以 6000.6.10f1 開啟。
2. 把 `Arduino/StressTest_Opto` 或 `Arduino/StressTest_RF` 燒錄到 Nano（見下一節）。
3. 在 Unity 開啟 `Assets/Scenes/StressTest.unity`，按 **Play**。測試介面會自動出現，不需要手動掛任何元件。
4. 在左側選擇入口和 COM port，按「連線」。狀態燈變成綠色就可以開始。
5. 接下來每一步要做什麼、看哪裡，照[操作流程](#操作流程)的步驟 0～12 一步一步做。

> 第一次正式測試前，建議先照 [Docs/BenchAcceptance.md](Docs/BenchAcceptance.md) 做一次台架驗收和前測。

## 硬體接線與燒錄

| 韌體 | 腳位 | 用途 |
|---|---|---|
| `StressTest_Opto` | D3 | 加速 |
| | D4 | 減速 |
| | D5 | 停止 |
| | D6 | 啟動 |
| `StressTest_RF` | D10 | RF 發射（TX） |

**燒錄設定**
- 開發板選「Arduino Nano」，處理器選「ATmega328P」。上傳失敗的話改選「ATmega328P (Old Bootloader)」。
- 序列埠 baud 是 **115200**。燒錄完成後，用序列埠監控視窗（行尾選「Newline」）應該會看到：
  - 光耦版：`READY,OPTO,0.3.0,press_ms=120;action_ms=120`
  - RF 版：`READY,RF,0.3.0,bits=24;repeat=2;release_ms=250;action_ms=340`
- **燒錄完記得關掉序列埠監控視窗**，否則 Unity 連線時會顯示「被其他程式占用」。

## 操作流程

以下照實際測試的順序，一步一步說明。每一步分三點：

- **做什麼**：你要動手做的事。
- **看哪裡**：畫面上要看的位置。
- **怎麼看**：畫面長什麼樣子才算正確，不對的話怎麼處理。

> 截圖是用模擬韌體拍的，畫面上的數字只是示範。全部 25 個畫面的完整說明在 [Docs/UI-Screens.md](Docs/UI-Screens.md)。

### 先認識畫面

![畫面的三個區域](Docs/screenshots/ui/05_idle.png)

畫面固定分成三塊，之後每一步都會用到這三個名稱：

| 位置 | 名稱 | 裡面有什麼 |
|---|---|---|
| 最上面一條 | **狀態列** | 左邊是**圓形燈號**和連線狀態；右邊是「中斷連線」和紅色的「**緊急停止（空白鍵）**」 |
| 左邊大塊 | **「現在要做的事」** | 現在該做的那一件事。**綠色的大按鈕就是下一步要按的**，每個畫面只有一顆 |
| 右邊大塊 | **條件矩陣** | 4 種間隔 × 3 種次數，每一格寫著光耦、RF 各完成幾輪 |

燈號的顏色：⚪ 灰色是還沒連線，🟡 黃色是正在連線，🟢 綠色是已連線、可以測試，🔴 紅色是出問題了，看燈號旁邊的文字。

> **安全**：不管進行到哪一步，只要覺得不對勁，按鍵盤的**空白鍵**就是緊急停止。跑步機沒有反應的話，直接按跑步機本體的停止鍵。

### 步驟 0：開始前的準備（不用開程式）

**做什麼**
1. 把要測的入口韌體燒到 Nano：測光耦燒 `Arduino/StressTest_Opto`，測 RF 燒 `Arduino/StressTest_RF`。燒錄方法見[硬體接線與燒錄](#硬體接線與燒錄)。
2. **關掉 Arduino IDE 的序列埠監控視窗。** 沒關的話，程式會連不上。
3. 把 Nano 的 USB 線接到電腦，跑步機插電。
4. **跑帶上不要站人**，跑步機本體的停止鍵要放在你伸手按得到的地方。
5. 架好手機錄影，畫面要**同時拍到跑步機面板和電腦螢幕**。之後懷疑某一段的結果時，可以回頭看。

### 步驟 1：開啟測試程式

![尚未連線](Docs/screenshots/ui/01_disconnected.png)

**做什麼**：在 Unity 開啟 `Assets/Scenes/StressTest.unity`，按上方的 **Play** ▶；如果用的是建置好的執行檔，直接雙擊 `StressTest.exe`。

**看哪裡**：狀態列左上角的燈號，以及左邊「現在要做的事」。

**怎麼看**：燈號是**灰色**，旁邊寫「尚未連線」；左邊顯示「連線到 Arduino」。看到這個畫面就是正常的。

---

### 步驟 2：連線到 Arduino

**做什麼**
1. 左邊「**1. 選擇入口**」：測光耦按「光耦」，測 RF 按「RF」。**必須和板子上燒的韌體一致。**
2. 「**2. 選擇 COM port**」：按 Nano 所在的 COM port，例如 `COM3`。列表是空的，就按右邊的「重新整理」。
3. 按綠色的「**3. 連線**」。

**看哪裡**：狀態列的燈號和燈號旁邊的文字。

**怎麼看**
- 燈號先變**黃色**，顯示「等待韌體回報身分…」，大約 2 秒。這是 Nano 正在重開機，屬於正常現象。
- 接著變**綠色**，顯示「已連線：光耦韌體 v0.3.0」（或 RF），下方小字是韌體參數。**看到綠燈就成功了**，畫面會變成步驟 3 的樣子。

**連不上時：**

| 畫面 | 燈號／文字 | 原因 | 怎麼處理 |
|---|---|---|---|
| ![入口不符](Docs/screenshots/ui/02_entry_mismatch.png) | 🔴「入口不符：選了光耦，板子是 RF 韌體」 | 選的入口和板子上的韌體不一樣 | 按左邊的「中斷連線，重新選擇」，改選正確的入口，或換一塊板子 |
| ![連線逾時](Docs/screenshots/ui/04_handshake_timeout.png) | 🔴「逾時：4 秒內沒有收到韌體回報」 | 板子上不是測試韌體，或 baud 不對 | 重新燒錄測試韌體，再連一次 |
| （紅字顯示在左邊） | 「COM3 被其他程式占用」 | 序列埠監控視窗還開著 | 關掉 Arduino IDE 的序列埠監控視窗，再按連線 |

---

### 步驟 3：確認下一輪要測什麼，按「開始下一輪」

![已連線、閒置](Docs/screenshots/ui/05_idle.png)

**做什麼**：先看清楚左邊寫的條件，確認無誤後按綠色的「**開始下一輪**」。

**看哪裡**：左邊「現在要做的事」由上往下有四行：
1. 大字「**下一輪：光耦、間隔 1 ms、120 次**」：這一輪的入口、間隔、總次數。
2. 「**加速 60 次、減速 60 次，分 6 段（每段 20 筆）**」：這一輪總共要送幾次加速、幾次減速，分成幾段。
3. 「第 1 輪……預熱加速 10 次到 2.0 後開始計分（2.0↔4.0）」：這是同一個條件的第幾輪，以及速度會在什麼範圍內來回。
4. 小字「依整體排程下一輪輪到 RF；也可以先繼續用光耦」：照整體排程該換板子時，才會出現這一行。

**怎麼看**
- 入口要和你接的板子一致。條件不用自己挑，系統會照排程選好。
- 想指定某個條件（例如補做），改按右邊矩陣裡的那一格。
- 矩陣每一格的「光耦 1/3、RF 1/3」，代表這個條件兩個入口各完成了 1 輪，目標是 3 輪。

### 步驟 4：啟動倒數（不用操作）

![啟動倒數](Docs/screenshots/ui/07_round_starting.png)

**做什麼**：什麼都不用做，等就好。

**看哪裡**：左邊的大字「已送出啟動，等跑帶穩定：4 秒」，以及**跑步機本體**。

**怎麼看**
- 跑步機的跑帶開始轉，面板顯示 **1.0 km/h**（開機速度）。
- 倒數到 0 之後，會自動進入預熱。
- 跑帶**沒有轉**：代表啟動指令沒有生效，按空白鍵緊急停止，回頭檢查接線。

### 步驟 5：預熱（不用操作）

![預熱](Docs/screenshots/ui/08_round_warming_up.png)

**做什麼**：什麼都不用做。系統每秒按一次加速，共 10 次。

**看哪裡**：左邊的大字「**預熱加速：4 / 10**」，以及跑步機面板。

**怎麼看**：數字每秒加 1，面板速度也每秒加 0.1，從 1.0 一路升到 **2.0**。預熱不計分，只是先把速度帶到起點。

### 步驟 6：確認起點速度是 2.0

| ① 輸入面板讀數 | ② 確認 |
|---|---|
| ![輸入起點讀數](Docs/screenshots/ui/09_round_warmup_reading.png) | ![確認起點](Docs/screenshots/ui/10_round_warmup_confirm.png) |

**做什麼**
1. 抬頭看**跑步機面板**上的速度。
2. 把讀數打進左邊的輸入框，例如面板顯示 2.0，就打 `2.0`，也可以打 `20`。輸入框已經自動選好，直接打字就可以。
3. 按 **Enter**。
4. 畫面變成「你輸入的面板速度：2.0 km/h」，確認沒打錯，再按一次 **Enter**。

**看哪裡**：左邊大字「**請看面板，預期 2.0 km/h**」，這是系統預期面板應該顯示的數字。

**怎麼看**
- 面板就是 2.0：照打，按兩次 Enter，開始第一段。
- 打錯了：在第二個畫面按 **Esc**，回去重打。
- **面板不是 2.0**（例如 1.8）：按 Enter 之後會出現下面這個畫面，二選一：

  ![預熱讀數不符](Docs/screenshots/ui/16_round_warmup_mismatch.png)

  - 「**重新預熱（補足差額）**」：建議選這個。系統會補按差的次數，例如 1.8 → 2.0 補 2 次加速，然後回到 ① 重新確認。
  - 「**以 1.8 為起點繼續**」：不補，直接用 1.8 當起點開始計分。

---

### 步驟 7：段執行中（不要操作）

![段執行中](Docs/screenshots/ui/11_round_running_segment.png)

**做什麼**：**什麼都不要按。** Arduino 正在用設定好的間隔，連續送出這一段的 20 筆指令。

**看哪裡**：左邊上方「本輪：間隔 1 ms、80 次　**段 1 / 4**」，代表現在是第幾段、總共幾段；大字「**執行中：加速 20 筆**」；以及藍色進度條。

**怎麼看**
- 進度條是**預估**的時間，跑滿之前畫面就可能先換掉，這是正常的。
- 這時跑步機面板的速度會一路往上加（或往下減）。
- 有異狀就按**空白鍵**緊急停止。

### 步驟 8：看面板，輸入這一段結束時的速度

![輸入段終點讀數](Docs/screenshots/ui/12_round_segment_reading.png)

**做什麼**
1. **等面板的數字停下來不再變**，再讀數字。
2. 把面板顯示的速度打進輸入框，例如面板顯示 3.7，就打 `3.7` 或 `37`。
3. 按 **Enter**。

**看哪裡**：左邊大字「**請看面板，預期 4.0 km/h**」，以及跑步機面板。

**怎麼看**
- 預期 4.0、面板也是 4.0：這一段的指令全部收到了。
- 預期 4.0、面板是 3.7：差 0.3 km/h，代表漏了 3 筆。這正是要測的掉包，**照實輸入就好**，不用改成預期值。
- 輸入框上方出現黃色或粗體的提醒，例如「Arduino 只回報 17 筆」或「預期低於最低速度 1.0」，請先看步驟 9 的旗標說明，然後一樣**照面板的實際讀數輸入**。

---

### 步驟 9：確認系統推算的掉包數

![確認掉包](Docs/screenshots/ui/13_round_segment_confirm.png)

**做什麼**：檢查畫面上的數字，沒問題就按 **Enter** 進入下一段；打錯就按 **Esc** 回步驟 8 重打。

**看哪裡**
- 大字「**面板 3.7 km/h → 推算掉包 3 筆**」：這一段的結果。
- 下一行「預期變化 +2.0 km/h，實際 +1.7 km/h；Arduino 回報 20 筆」：
  - **預期變化**：照指令應該變多少（20 筆 × 0.1 = 2.0）。
  - **實際變化**：面板實際變了多少。
  - **Arduino 回報**：Arduino 說它真的送出了幾筆。

**怎麼看**
- **Arduino 回報 20 筆，但掉包 3 筆**：Arduino 確實送出了 20 筆，跑步機只反應了 17 筆，這就是**跑步機那一端的掉包**，正是這個實驗要量的東西。
- 出現粗體的旗標（見下圖），代表這一段的掉包數**不可信**：

  ![旗標](Docs/screenshots/ui/18_round_clamped_confirm.png)

  | 旗標 | 意思 | 建議 |
  |---|---|---|
  | 「**可能觸底／觸頂**」 | 理論終點超出 1.0～12.0，多出來的指令被跑步機吃掉了 | 記下來，結束後考慮作廢這一輪 |
  | 「**Arduino 回報不足**」 | Arduino 回報的筆數比應送的少，問題可能在電腦或序列埠，不一定是跑步機 | 對照錄影，考慮作廢 |

### 步驟 10：重複步驟 7～9，直到所有段跑完

**做什麼**：照步驟 7 → 8 → 9 的順序，把剩下的段做完。

**看哪裡**：左邊上方的「**段 2 / 4**」，以及「**加速 已送 20／預計 40　減速 已送 0／預計 40**」。

**怎麼看**
- 加速段和減速段輪流：第 1 段加速（2.0 → 4.0），第 2 段減速（4.0 → 2.0），第 3 段又加速，依此類推。
- 段數依總次數而定：40 次是 2 段，80 次是 4 段，120 次是 6 段。
- 「已送」是 Arduino 回報實際送出的次數，跑完時應該和「預計」一樣。
- 每一段都從上一段**你輸入的實際讀數**開始算，所以前一段漏掉的部分不會重複算進下一段。

---

### 步驟 11：看本輪總結，離開這一輪

![本輪總結](Docs/screenshots/ui/14_round_summary.png)

**做什麼**
1. 確認跑步機的**跑帶已經完全停下來**。最後一段結束後，系統會自動送出停止指令。
2. 結果沒問題：按綠色的「**跑帶已停止，回到設定**」。
3. 結果有問題，例如有段出現旗標、看錯面板、中途有人碰到跑步機：在「作廢原因」欄寫下原因，按「**作廢此輪**」。

   ![作廢此輪](Docs/screenshots/ui/15_round_void_reason.png)

**看哪裡**
- 大字「**本輪完成：總掉包 3 / 80 筆**」：這一輪的總結果。
- 下面每一行是一段，例如「段 1：加速 20 筆，2.0 → 3.7，掉包 3」。
- 「加速：預計 40、Arduino 實送 40　減速：預計 40、Arduino 實送 40」：兩個數字應該一致。
- 「紀錄位置」：CSV 存在哪個資料夾。

**怎麼看**
- **一定要按其中一顆按鈕**，這一輪才會寫進每輪紀錄、計入右邊矩陣的進度。
- 作廢的輪次，原始資料還是會保留，只是不計入進度，之後需要重做那個條件。

---

### 步驟 12：跑下一輪，或換板子

**做什麼**：回到步驟 3 的畫面後，按「開始下一輪」繼續測。

**看哪裡**：左邊有沒有出現小字「**依整體排程下一輪輪到 RF（或光耦）**」，以及右邊矩陣的進度。

**怎麼看**
- 沒有這行小字：照常按「開始下一輪」。
- 出現這行小字：代表照排程該換另一個入口了。你可以先繼續用目前的板子，等這個入口的條件都做完再換。要換的話：按狀態列的「中斷連線」→ 換板子或重新燒錄 → 回到步驟 2。
- 左邊顯示「**光耦已完成所有條件**」：這個入口全部做完了，換另一個入口。
- 可以分好幾天測。下次打開程式時，右邊矩陣會自動從紀錄檔還原進度（「已從 N 個紀錄檔還原 M 輪完成紀錄」）。

## 紀錄檔（CSV）

所有紀錄都寫在專案根目錄的 `TestLogs/` 底下。右側面板有「開啟紀錄資料夾」按鈕可以直接打開。

紀錄檔的格式：
- 編碼是 UTF-8 BOM，用 Excel 直接開啟，中文不會變亂碼。
- 每寫入一列就立刻存檔，所以即使 Unity 當掉，已經確認過的段也不會遺失。
- 每次啟動 Unity 會產生一組新檔，檔名帶有時間戳記。

| 檔案 | 一列代表 | 主要欄位 |
|---|---|---|
| `commands_*.csv` | 一筆指令 | `round_id`、`entry`、`gap_ms`、`segment_index`、`seq`、`direction`、`start_us`、`end_us`、`gap_us`（與上一筆的實際間隔） |
| `segments_*.csv` | 一段 | `start_speed`、`expected_end`、`actual_end`、`drops`、`reported_count`、`report_short`、`timed_out`、`possibly_clamped`、`mean_gap_us`、`max_gap_us` |
| `rounds_*.csv` | 一輪 | `entry`、`gap_ms`、`total_count`、`total_sent`、`total_drops`、`warmup_reading`、`end_reading`、`up_planned`／`down_planned`（預計加速／減速次數）、`up_sent`／`down_sent`（Arduino 實際回報送出的次數）、`warmup_up`／`warmup_down`（預熱單發，不計分）、`status`（`completed`／`voided`）、`void_reason` |
| `manual_segments_*.csv` | 手動單段的一段 | 與 `segments_*.csv` 相同，但 `round_id` 和 `segment_index` 欄位留空 |

**整理論文用的掉包表**
1. 把所有 `rounds_*.csv` 合併成一份。
2. 篩選出 `status = completed` 的列。
3. 建立樞紐分析表：列放 `entry`，欄放 `gap_ms`，值放 `total_drops` 和 `total_sent` 的加總。

詳細步驟見 [BenchAcceptance.md 的 F 節](Docs/BenchAcceptance.md#f-紀錄檔)。

> `TestLogs/` 是實驗資料，目前沒有加進 `.gitignore`。要不要納入版本控制，請依研究室的資料管理方式決定。

## 掉包怎麼算

```
推算掉包數 = | 預期變化 − 面板實際變化 | ÷ 0.1   （四捨五入）
```

- **預期變化**：方向 × 筆數 × 0.1 km/h。
- **實際變化**：這段結束時的讀數減去這段開始時的讀數。每段的起點用上一段結束時的**實際讀數**，不用理論值，這樣誤差才不會一段段累積下去。

段結果的旗標：

| 旗標 | 意思 |
|---|---|
| `possibly_clamped`（可能觸底／觸頂） | 起點加上預期變化後超出 1.0～12.0 km/h（跑步機最低 1.0），多出來的指令會被跑步機吃掉，這段推算出來的掉包數不可信。 |
| `report_short`（回報不足） | Arduino 回報的筆數少於應送筆數，或逾時沒有回報。問題可能出在序列埠或韌體，不一定是跑步機掉包。 |
| `timed_out` | 在「筆數 ×（單筆動作時間 + 間隔）× 2 + 2 秒」內沒有收到 `DONE`。 |

Arduino 用 `micros()` 記錄每一筆的開始和結束時間。這些時間戳會先存在 RAM，等整段跑完才一次回傳；執行期間 Arduino 不會輸出任何序列資料，避免傳輸時間把間隔拉長。

## 開發者：測試與建置

### 自動化測試

測試只透過一個接縫進行：`ISerialLink`，也就是「送一行、收一行」。測試用 C# 寫的 `FakeArduino` 模擬韌體，驅動整個流程，不需要接任何硬體。

- **在 Unity 中執行**：Window → General → Test Runner → EditMode → Run All。
- **用命令列執行**：先關閉開著這個專案的 Unity 編輯器，再執行：

```powershell
& "<Unity 安裝路徑>\6000.6.10f1\Editor\Unity.exe" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults results.xml -logFile unity.log
```

目前共有 113 個 EditMode 測試，全部通過。

### 建置 Windows 執行檔

```powershell
& "<Unity 安裝路徑>\6000.6.10f1\Editor\Unity.exe" -batchmode -quit -projectPath . -executeMethod StressTest.EditorTools.StressTestBuild.BuildWindows -stresstest-build-path Build\StressTest.exe
```

**版面導覽**：執行檔加上參數 `-stresstest-tour <資料夾>` 啟動時，會接上內建的模擬韌體 `SimulatedArduino`，自動走過所有畫面，逐一截圖（共 25 張）後結束。[Docs/UI-Screens.md](Docs/UI-Screens.md) 裡的截圖就是這樣產生的：

```powershell
Build\StressTest.exe -screen-fullscreen 0 -screen-width 1920 -screen-height 1080 -stresstest-tour Docs\screenshots\ui
```

**單張截圖**：執行檔加上參數 `-stresstest-screenshot <路徑>`，啟動後會自動截一張圖然後結束，用來在不同解析度下檢查版面。例如：

```powershell
Build\StressTest.exe -screen-fullscreen 0 -screen-width 1280 -screen-height 720 -stresstest-screenshot shot.png
```

### 架構原則

- **`StressTest.Core`**：協定、狀態機、判定、CSV 都放在這裡。這個組件**不引用 UnityEngine**，可以獨立測試。
- **`StressTest.Runtime`**：只負責顯示 Core 的狀態，以及把操作轉交給 Core，不放任何判定邏輯。

## 序列協定

115200 baud，每行以 `\n` 結尾。兩支韌體使用同一套協定。

| Unity → Arduino | 意義 |
|---|---|
| `HELLO` | 要求韌體回報身分 |
| `ONE,<START\|UP\|DOWN\|STOP>` | 單發一次 |
| `RUN,<UP\|DOWN>,<n>,<gap_ms>` | 連續送 n 筆（n ≤ 32）；每筆動作完成後休息 gap_ms 毫秒 |
| `ABORT` | 中止執行中的 RUN |

| Arduino → Unity | 意義 |
|---|---|
| `READY,<OPTO\|RF>,<版本>,<參數>` | 開機時或回應 HELLO |
| `ACK,<原指令>` | 已接受指令 |
| `T,<i>,<start_us>,<end_us>` | 第 i 筆的開始與結束時間；整段跑完後才一次送出 |
| `DONE,<n>` | RUN 完成 |
| `ABORTED,<n>` | RUN 被中止，n 為中止前已完成的筆數 |
| `ERR,<原因>` | 例如 `BAD_COMMAND`、`BAD_RUN`、`BUSY`（RUN 執行期間收到其他指令）、`UNKNOWN` |

## 已知限制

- **以段為單位判定**：跑步機本身不會回報收到哪一筆指令，只能從每段的面板讀數推算。如果同一段裡同時「漏一筆」又「多一筆」，兩者會互相抵銷，看不出來。要逐筆核對只能看錄影。
- **RF 的 `action_ms=340` 是推算值**：由 frame 長度和釋放時間算出，只用於估計逾時和顯示進度條。實際耗時請看 CSV 裡的時間戳，並在台架驗收時填入實測值。
- **面板輸入的規則**：沒有小數點、且數值 ≥ 10 的整數會自動除以 10（例如 `27` → 2.7）。所以要輸入 10～12 km/h 時，請打成 `10.0`。本測試的速度範圍是 2.0～4.0，平常不會遇到。
